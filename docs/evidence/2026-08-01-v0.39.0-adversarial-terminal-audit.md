## DedupとVerify裁定

### F01 — 監査未受理planが完走済みとして消え、Phase進捗も監査待ちを表示しない

- Raw: `D1`, `D6`, `P1`, `P2`
- 裁定: **確認・契約重大**
- 実在性:
  - `src/todo-gantt-scope.mjs`の`auditPending`は`lattice.todo_plan.v7`を対象外にする。
  - `renderPhaseProgress`はv4/v5/v7の`plan.phases`だけを走査し、v6の暗黙`terminal-audit`を表示しない。
  - 公開`/projects/lattice/`はstore上`terminal-audit=gate_ready`なのに「進行中のPhaseはありません」と表示した。
- 修正価値: 全ToDo doneと終端監査受理を分けるADR 0147の利用者向け不変条件を破るため、修正必須。

### F02 — 監査待ちだけが残ったprojectがTTL後にdashboardから消える

- Raw: `D7`, `P3`
- 裁定: **確認**
- 実在性: `bin/lattice-dashboard.mjs`の可視性判定は`active_set.length > 0`だけで、Phaseの
  `gate_ready`/`reviewing`/`rejected`を見ない。registryのTTL満了後に対象外となり、最後のprojectならdaemonも停止する。
- 修正価値: 監査待ちを運用画面から消すため修正必須。

### F03 — 畳んだ工程の案内が同一ページ展開と二台目server起動を矛盾して示す

- Raw: `D5`, `D8`
- 裁定: **確認・非契約重大**
- 実在性: 同じHTMLにexpanded diagramがある場合も、右ペイン個別工程は`gantt serve --scope all`を案内する。
  legend側の非展開分岐は通常の公開renderでは到達しない。
- 修正価値: 誤操作と不要なdaemon起動を誘うため、同一ページのバッジへ案内を統一する。

### F04 — PROJECT_ROOT_CONFLICTの型・復旧導線・helpが失われる

- Raw: `D2`, `D3`, `C1`, `C2`, `M4`, `P4`
- 裁定: **確認・契約重大**
- 実在性:
  - registryは`PROJECT_ROOT_CONFLICT`を投げるが、todo wrapperはdetailを`project_id`だけへ差し替える。
  - `status --json`は`status_internal_failure`へ一般化し、同じ衝突を起こす`todo verify`を次の一手にする。
  - `todo dashboard adopt --help`は`INVALID_ARGUMENTS`となり、自分自身をnext_actionへ返す。
  - `scripts/verify-cli-surface.mjs`はdashboard入口を列挙しないためgreenでも欠落を検出しない。
- 修正価値: fail-closedした利用者が正規復旧できないため修正必須。

### F05 — 廃止static ganttのcatch-allが動的serveの不正引数を誤診断し、static系では拒否前に副作用を起こす

- Raw: `D4`, `C4`, `C5`, `C7`, `P5`
- 裁定: **確認・契約重大部分あり**
- 実在性:
  - `gantt serve --port abc`と`--port 99999`が`INVALID_ARGUMENTS`でなく`STATIC_GANTT_RETIRED`になる。
  - static退役errorのnext_actionは動的viewerでなく`todo status --json`である。
  - `serve`はmanual serve判定済みで自動起動しない。一方、bare `gantt`、`gantt status`、
    static `gantt --out`等はcatch-all action実行前にdashboard自動起動経路へ入る。
- 修正価値: 「個別HTMLを生成させない」「動的工程表を唯一の入口にする」という今回の契約へ直結する。

### F06 — plan createの一般schema違反が構造化diagnosticを返さない

- Raw: `C3`
- 裁定: **確認・契約重大**
- 実在性: `runPlanCreate`はdesign memo gate以外を`INPUT_INVALID/plan_create_schema_invalid`だけで返し、
  製品契約が要求する`violation_kind`、`pointer`、`expected`、`actual`、`next_action`を持たない。
- 修正価値: AIが入力を自力訂正できるauthoring contractの中核なので修正必須。

### F07 — plan createが必ず拒否する旧schemaを現役入力として配り、helpの既定版も古い

- Raw: `C6`, `M6`
- 裁定: **確認**
- 実在性: schema v1〜v3を完全入力schemaとして配布する一方、`runPlanCreate`はv4以外を先頭gateで拒否する。
  helpは既定をv3と記載するが実装既定はv4である。
- 修正価値: 互換参照として残すこと自体は妥当だが、現役入力と誤認させる表示は修正する。

### F08 — 製品契約内でstatic Ganttとplan schema世代が自己矛盾する

- Raw: `C8`, `P6`
- 裁定: **確認**
- 実在性: `docs/00_product-contract.md`前半はHTML再生成可能な`gantt`とv5を記述し、後半はstatic退役とv7を記述する。
- 修正価値: AIへの正規入口を誤らせるため修正必須。

### F09 — v5→v7でdesign_memoを追加すると既存lifecycle stateをcarryできない

- Raw: `M1`
- 裁定: **確認・契約重大**
- 実在性: `phaseV3CarrySemantics`の通常carryはtask全体を比較するため、新設`design_memo`差分を
  identity/topology差分として`carry_semantics_changed`で拒否する。
- 修正価値: 既存Phase planを状態保持したままAI安全authoringへ移行できないため修正必須。

### F10 — migrate dry-runが依存循環でnull参照crashする

- Raw: `M2`
- 裁定: **確認・契約重大**
- 実在性: `plannedPlan`を代入した後にdispatch shape計算が失敗すると、結果組立てがnullの
  `dispatchShape.task_count`を参照する。
- 修正価値: dry-runが診断面でなくinternal failureになるため修正必須。

### F11 — 登録taskが除外taskを親・依存・joinとして参照しても抽出validationを通過する

- Raw: `M3`
- 裁定: **確認・契約重大**
- 実在性: extraction validatorは全task集合への参照だけを確認し、compile時は登録taskだけへ絞る。
  その結果、登録taskの`parent_task_id`等がplan外を指し、後段で無診断TypeErrorになる。
- 修正価値: disposition cutoverの参照整合性を壊すため、compile前にtyped violationとして拒否する。

### F12 — design_memoの公開上限がschema間・runtime間で不一致で、byte超過を「設計メモなし」と誤診断する

- Raw: `M5`, `S3`, `P7`
- 裁定: **確認・契約重大**
- 実在性:
  - extraction v3とtodo revision v2は`maxLength: 262144`、phase revision v3とplan create v4は
    `maxLength: 16384`、runtimeは16384 UTF-8 byteである。20KB ASCIIは前二者のschemaへ適合してruntimeで落ちる。
  - runtime byte上限を超えた日本語memoを、migrate dry-runとplan createが`design_memo_required`として返し、
    byte数もpointerも示さない。
- 留保: JSON Schemaの`maxLength`は文字数、runtimeはbyte上限なので、`$comment`によるbyte制約の明示自体は残す。
- 修正価値: 内容を露出せず`byte_length`と`max_bytes`を返せば、AIが正しく縮約できる。

### F13 — design_memo削除禁止gateが実CLI revision経路で到達不能

- Raw: `S2`
- 裁定: **確認・契約重大**
- 実在性: 削除禁止を持つ`createSuccessorTodoPlan`はtestからしか呼ばれない。実CLIが使う
  `applyTodoRevision`、`applyPhaseTodoRevisionV3`、`applyTodoRevisionSet`はpredecessor schemaを照合せず、
  v7→v5またはv6→v3のdesired planを受理して全memoを落とせる。
- 修正価値: ADR 0150の「設計メモを後継schemaで暗黙消失させない」を直接破るため修正必須。

### F14 — dashboardのdesign_memoがprose budgetの診断分類を迂回する

- Raw: `S4`
- 裁定: **確認・診断品質**
- 実在性: `src/todo-gantt-html.mjs`の`TODO_GANTT_PROSE_MAX_BYTES`計算はnarrativeとnoteだけを加算し、
  右ペインでrenderするdesign memoを数えない。HTML全体には別の総量上限が既にあるため無制限にはならないが、
  prose固有errorでなくHTML総量errorまで膨らみ、原因と復旧対象を誤らせる。
- 修正価値: bounded rendering自体は維持される。AIへ正しい縮約対象を示すため診断分類を修正する。

### F15 — extraction文書がv1入力を現役として示し、v3/design_memo/NO_PLANを説明しない

- Raw: `S5`
- 裁定: **確認**
- 実在性: `docs/todo-extraction-v1.md`は今回更新された文書だがschema v1を入口にしたままで、
  現行migrateが要求するv3とdesign memo契約を示さない。文書どおりの入力は`DESIGN_MEMO_REQUIRED`になる。
- 修正価値: AI authoringの入力文書が実行契約と逆なので修正必須。

### F16 — migrate dry-runがstore／I/O障害までtopology不正へ誤分類する

- Raw: `K1`（Critic round 1）
- 裁定: **確認・契約重大**
- 実在性: `migrateDryRun`のcatchはtopology compileとstore read／freshness確認を一括で囲み、後者の失敗も
  `topology_invalid`、pointer `/hard_dependencies`、`correct_extraction_topology`として返す。
- 修正価値: 正しい入力を修正し続ける自己ループになる。topology検査だけを狭く捕捉し、store／I/O障害は
  別のtyped diagnosticとして返す。

### F17 — 取り消した旧監査証拠が現在も「受理」と主張する

- Raw: `K2`（Critic round 1）
- 裁定: **確認・監査重大／修正済み**

### F18 — Phase進捗rendererがderived phaseとplan metadataの不一致でnull参照する

- Raw: `K3`（Critic round 1）
- 裁定: **確認・堅牢性**
- 実在性: `renderPhaseProgress`はplan側phaseを走査してderived stateを無条件参照する。暗黙終端監査を表示する
  拡張で逆向き参照を増やすと、欠落時に`state.status`でTypeErrorになりうる。
- 修正価値: derived `member.phases`を正本に走査し、明示phaseの表示metadataだけをplanから補う。

### F19 — 設計メモの消失・置換を通常carryと明示的改訂で区別していない

- Raw: `K4`（Critic round 1）
- 裁定: **確認・契約重大**
- 実在性: 非phase revisionの`taskSemantics`とphase revision v3の`reconciliationMetadata`枝は
  `design_memo`を比較対象に含めず、通常carryでもmemo全置換を黙って通せる。一方、全変更を拒否すると
  設計メモを訂正するたびにlifecycle stateを捨てる別の欠陥になる。
- 不変条件: 設計メモは黙って消失・置換できない。predecessorにmemoが無いlegacyからの初回追加は通常carryを
  許す。memo既存時の変更は通常carryで拒否し、明示的な`carry_reconciled_metadata`だけjournalにpolicyを残して
  stateを引き継ぐ。schema後退による全消失も同じgateで拒否する。

## Critic round 1の裁定

独立CriticはF01〜F15のDedup／Verifyを読み、7点を指摘した。全件の採否は次のとおり。

- F05: 一部採用。`gantt serve --port ...`自体はmanual serve判定済みでdaemon副作用はない。副作用の実在範囲を
  bare `gantt`、`gantt status`、static `gantt --out`等へ訂正し、serve不正引数の誤診断とは分離する。
- F09/F13: 採用。legacyへの初回memo追加だけをcarry可能にし、v7→v7のmemo置換をcarry不可にする（F19）。
- F14: 採用。HTML総量上限を確認し、無制限ではなくprose診断の不一致へ重大度を訂正した。
- store／I/O誤診断、旧証拠の未撤回、phase stateのnull参照: 新規所見F16〜F18として採用した。

Criticが見つけた盲点を反映したため、同じCriticへround 2として裁定漏れだけを再確認させる。新規の広域探索は
追加せず、二巡目はこの差分が盲点を閉じたかだけを検査する。

## Critic round 2の裁定

round 2は6点を返し、修正工程へそのまま着手することを拒否した。全件を採用した。

- F19の「memo変更は常にcarry拒否」は設計メモを凍結するため撤回し、通常carryと明示的な
  `carry_reconciled_metadata`を分ける契約へ訂正した。
- `carry_reconciled_metadata`枝もF19の射程へ含め、F13のschema後退と「黙った消失・置換禁止」という
  単一不変条件へ統合した。
- F14/F18は`audit-01`、F16/F19は`audit-03`、F17は`audit-04`へ割り当て、Latticeのdesign memo自体を
  successor planで改訂する。append noteだけで矛盾する旧memoを残さない。
- F17は既に撤回bannerを実装済みとして状態を更新した。

改訂planがstoreへ適用されるまでは実装へ着手しない。適用後、同じCriticへこの差分だけの最終確認を求める。
