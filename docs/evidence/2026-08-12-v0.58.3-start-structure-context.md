## Peertable実工程smoke

Peertable commit `032854811e7d619468ca9ac4f4aade52e15187ca`の独立cloneへ、現行の
`.lattice/todo`を複製して実施した。対象は
`peertable-dm-delivery-fx4e-20260811/k1`である。生のPeertable storeは変更していない。

着手結果は次を返した。

- schema: `lattice.todo_mutation_result.v5`
- task status: `in-progress`
- `structure_context.status`: `available`
- `structure_context.enabled`: `true`
- `structure_context.freshness`: `stale`
- `stale_reasons`: `current_head_sha`
- `structure_context.task`: `k1`のcanonical構造。outcome、inputs、operations、outputs、failures、first live E2E、non-goals、code anchorsを含む
- `next_actions`: `lattice todo structure realize --plan peertable-dm-delivery-fx4e-20260811 --task k1 --input <realization.json>`

`stale`は複製先HEADが構造compile時のHEADと異なることを正しく示した。計画構造を隠さず返しながら、
実体との差分をrealizationで更新すべきことも同じ返却で明示できている。

## 公開操作と補足

clean release worktreeで実dependency directoryを用意し、対象commit自身のSensorをbuildして検証した。
最初のbridge reconfigureは`BRIDGE_LAUNCHCTL_BOOTSTRAP_FAILED`を返したが、その直後の独立statusでは
0.58.3 processが起動済みだった。同一操作を再試行すると成功し、最終statusでもreachable、running、
0.58.3、runtime driftなしを確認した。失敗を成功へ丸めず、外部launchctl境界の一過性失敗として記録する。

## Rollback

0.58.3固有の起動不能またはデータ破壊を確認した場合は、直前版0.58.2をglobal installし、bridgeを再登録する。
npm unpublish、remote mainのforce push、履歴巻き戻しは行わない。修正版は新versionとして公開する。
