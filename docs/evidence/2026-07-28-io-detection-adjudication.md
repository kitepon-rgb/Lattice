# I/O検知の採否を裁定する（2026-07-28）

`write-coverage` planのwc-002に対する裁定記録。

## 設問（2026-07-27に立てた形）

> I/O検知を導入するか、checkpoint間隔を詰めるか。**holdで捨てた作業量を実測し、
> checkpoint間隔を詰めても割に合わないと分かった時**に着手する。

## 裁定

**I/O検知を採用する。** ただし設問の立て方が2箇所で誤っていた。

### 1. 二択ではなかった

「I/O検知 **か** checkpoint間隔を詰めるか」と書いたが、両者は直交する。

| | 効くところ |
|---|---|
| I/O検知 | 平均の検出遅延。書き込みイベントが届けばmsで気づく |
| checkpoint間隔を詰める | **取りこぼした時の床**。fs eventはFSEventsのcoalesceやinotifyのキュー溢れで落ちる |

I/O検知を入れても、取りこぼした競合の最悪ケースは変わらない（worker完了まで）。間隔を詰めても
平均は改善しない（経路は処理速度で決まる）。**片方を選ぶ問題ではなかった。**

### 2. 順序が逆になった

計画では「実測してから裁定」だったが、実際は**実装が先行し、実測はその副産物として出た**。
理由を正直に書くと、実測に必要な数字（holdで捨てた作業量）は、**I/O検知が動く構成が無いと
そもそも測れなかった**——早期検知が無い状態では「早く気づいていたら何秒節約できたか」は
反実仮想でしかない。実装して初めて対照が取れた。

設問の立て方が実現不能だったことになる。同型の発火条件を書く時は、**その測定が現状の構成で
可能かを先に確かめる**。

## 実測（[受入証拠](2026-07-28-io-sentinel-live-run.md)）

worker 2並列、宣言scope外への書き込み、`hold_ms = 8000`。

| 段 | dispatchからの経過 |
|---|---|
| 実在警報（probeが`observed`と裁定） | 137 ms |
| `intake_frozen` | 662 ms |
| `hold_decided` | 663 ms |
| **（従来）worker完了まで** | **8,000 ms** |

**捨てる作業量は検出遅延に比例する。** 競合が始まってから気づくまでの間、両者が進めた分が
holdで無効になるからである。したがって:

- 従来: 上限は**workerの実行時間そのもの**。装置が決められない値であり、長い作業ほど大きい
- 現在: 上限は**検出経路の処理時間**。実測で0.66秒

**装置が決められない値が、装置が決める値になった。** これが採用の根拠である。

## 何が支配的か

経路の内訳を実測した（Lattice repo自身、82 module）。

| 段 | 実測 |
|---|---|
| probe（`git status --untracked-files=all --ignored=matching`） | 10 ms |
| `finding_record`（sensor全query再実行 + plan再compile） | query 1件 30〜50 ms |
| `conflict`（events.json書き込み） | ms級 |
| `hold`（barrier + `ps` snapshot） | 数十ms |

支配項は`finding_record`の再compileである。これは**freezeする前に検証している**（verify-then-freeze）
ためで、順序を変えれば数百ms速くなるが、代わりに「検証前に止める」経路——誤検知で無実のworkerを
止める道——を作ることになる。捨てるのが数百ms分である以上、割に合わない。**現状の順序を維持する。**

## checkpoint間隔（tick）の扱い

**保留する。** 平均遅延は改善しないので、入れる動機は「取りこぼした時の床」だけである。
コストはworktreeごとの`git status`（実測10ms）×間隔なので、数秒間隔なら無視できる。
ただし現時点で取りこぼしの実害は観測していないため、**発火条件を書いて保留する**:
fs eventの取りこぼしにより競合の検出がworker完了まで遅れた事例が1件観測されたら着手する。

## この裁定が主張しないこと

- **worktree外への書き込みは、依然として見えない。** `/tmp`、home、ネットワーク、他repositoryへの
  書き込みは`git status`に映らない。これは遅延の問題ではなく観測範囲の問題であり、
  [ADR 0140](../adr/0140-canonical-write-observation-is-recorded-not-assumed.md)の保留のまま残る。
  I/O検知を入れても変わっていない——今回のsentinelもworktree内しか見ていない。
- Linuxでの数値。実daemonを起こす計測はmacOSでのみ行った。
