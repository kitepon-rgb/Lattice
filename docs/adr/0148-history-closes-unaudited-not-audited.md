# ADR 0148: 監査していない歴史は「監査なしで閉じた」として閉じる——監査済みに化けさせない

- 状態: 採択（2026-07-30）
- 関連: [ADR 0147](0147-audit-is-on-by-default.md)（終端監査は既定でON——本ADRはその欠陥を直す）、
  [ADR 0062](0062-decouple-phase-audit-from-task-scheduling.md)（Phase監査順とToDo schedulingの分離）
- 計画: [docs/plan_audit-baseline.md](../plan_audit-baseline.md)

## 文脈

ADR 0147の終端監査gateには欠陥があった。**過去に終わった工程まで「監査待ち」にしてしまう。**

過去の工程は監査できない。**監査対象のコードが既に変化している**からである。それでも監査を要求すると、
起きるのは次の2つのどちらかで、どちらもgateが誘発する事故になる。

1. 今のコードを見て「問題がある」と言い出す——実際には後の意図的な変更である（誤検出の事件）
2. 中身を見ずに`accept`を押す——**監査の意味を自分で壊す**

0.36.0のgateは2つを混ぜていた。「これから終わる工程は監査を通ってから完了にする」（正しい）と、
「過去に終わった工程も監査記録が無いなら監査待ち」（誤り）である。

実害は公開済みである。0.36.1をアップグレードした利用者の工程図は、過去の完了分で埋まる。
実測（2026-07-30）: Lattice自身が23 plan／104 ToDo、ServerManagerが1 plan／26 ToDo。
**何が起きたかも、何をすればよいかも画面に出ない。**

## 裁定

1. **第3の終端状態を作る。** Phaseは`accepted`（監査を通った）と`rejected`（監査が通らなかった）に加え、
   **`closed_unaudited`（監査なしで閉じた）**を持つ。専用のjournal event kindで記録し、理由の明示を必須とする。
2. **`accepted`へ絶対に化けない。** 記録は永久に区別でき、`closed_unaudited`が監査済みとして読める経路を
   作らない。とくに`phase_accept_dependencies`（Phase受理を必要とするToDo）は`accepted`だけで解錠され、
   `closed_unaudited`では解錠されない。
3. **`gate_ready`を前提にする。** 所属ToDoが全てdoneでない段階では、そのPhaseはまだ監査の地点に
   到達していない。`review`と同じ前提条件を課す。
4. **工程図では畳む。** `closed_unaudited`は監査待ちではないので、監査未了として図に留める対象から外す。
   これがノイズを消す唯一の正当な経路である——**gateが慢性的なノイズになれば読み飛ばされ、
   0.147で塞いだ穴が再発する。**
5. **やり直せる。** `phase_reopen`は`closed_unaudited`も初期状態へ戻す。後から本当に監査したくなった
   工程を、永久に締め出さない。
6. **一括入口を持つが、自動実行はしない。** 現在`gate_ready`かつphase eventを1つも持たないplanを
   まとめて宣言できる明示コマンドを持つ。104件を1件ずつ宣言させる設計は、誰にも実行されず
   gateをノイズへ変える。ただし装置が「古いから免除」と推定して自動で書くことはしない——
   どれを監査し、どれを歴史として畳むかは人／AIが決める。
7. **除外を指定できる。** 一括宣言は対象からplanを除外できる。ServerManagerの26 ToDoは最近の作業で
   コードも生きているため、基準線で流さず監査対象として残すのが正しい。一律免除はそれを取り逃がす。
8. **札が出た理由を画面で言う。** 監査待ちを返す面は、何が起きたか（過去の完了分へ終端監査の要求が
   及んだ）と次に打つコマンドをtyped detailへ載せる。驚きを説明しないgateは、原因を隠すのと同じである。

## この裁定が主張しないこと

- **「変化したか」を機械が判定するとは言っていない。** 監査対象が変化したかの判断は意味論的で、
  計画段階では決定不能である。装置は宣言を受け取って記録するだけとし、時間ベースの推定
  （「N日以上前だから免除」）も入れない。
- **監査の中身を採点しない**（ADR 0147の非目標を継承）。`closed_unaudited`は「監査しなかった」という
  事実の記録であって、監査結果の評価ではない。
- **既存のphase付きplanの挙動を変えない。** 新しい状態は明示宣言でしか到達せず、既存の
  `review`→`accept`／`reject`の経路と判定は変わらない。
- **store canonical形式・digest計算を変えない。** 増えるのは新設event kindの受け皿だけで、
  既存eventのbytesと既存digestの計算は変わらない。
- **dispatch可否に影響しない**（ADR 0062・0147裁定5を継承）。`closed_unaudited`の有無は
  `next_ready`／`active_set`／`dispatch_frontier`へ一切参照されない。
