# ADR 0138 — 変換の採用条件を五条件へ揃える（競合の増加と並列度の改善を見る）

- Status: Accepted
- Date: 2026-07-27
- Relates: [ADR 0032](0032-rc2-bounded-graph-compiler-and-three-way-seam.md)（bounded変換）・
  [ADR 0137](0137-real-transform-acceptance-contract.md)（本ADRはそのDecision 4を置き換える）

## Context

ADR 0137は変換の受入を4ゲート（外部挙動同等性・focused test通過・sensor鮮度・重複解消）とした。
その後、製品目標の正本である明細書を読み直したところ、採用判定は**五条件**を課していた。
4ゲートには2つ足りない。

- **競合作業対が増加しないこと。**
- **作業完了までに必要な実行段階数、または最も長い実行経路が改善したこと。**

どちらも欠かすと変換が目的を外す。

**競合の増加を見ない穴は具体的である。** ADR 0137 Decision 1の三面分割は、誰も宣言していない
依存先を「共有surface」へ抽出する。その共有surfaceは、**分割に関与していない別の作業対にとっての
新しい係争資源になりうる**。`overlap_reduced`は当該componentの残余conflictしか見ないので、
よそに競合を増やしても採用してしまう。局所の競合を消して全体の競合を増やす変換を、
機械が受理する経路が開いていた。

**並列度の改善を見ない穴は目的の取り違えである。** 競合辺が消えても、実行段階数が減らないなら
その変換は並列化を解放していない。外部挙動を変えうる変更を、便益なしに加えたことになる。
Latticeが解こうとしているのは競合の消去ではなく、並列開発の解放である。

## Decision

### 1. 採用条件を五条件にする

変換候補は次を**すべて**満たしたときだけ採用する。1つでも欠けたら棄却する。

1. `behavior_equivalent`: 変換前後で外部挙動条件を満たす
2. `focused_tests_passed`: 候補の`affected_tests`が変換後のworktreeで通る
3. `sensor_fresh`: 変換後のworktreeを再indexし、その索引で観測できる
4. `overlap_reduced`: 再indexした索引と同じ宣言で実compileし、**対象競合が消滅し、かつplan全体の
   競合作業対が変換前より増えていない**
5. `parallelism_improved`: 同じ作業集合・実行容量・前提関係の下で、実行段階数または最長実行経路が
   変換前より改善している

### 2. 競合の増減はplan全体で数える

`overlap_reduced`の判定範囲を、当該conflict componentからplan全体へ広げる。変換前の競合作業対の
集合と、変換後に再compileして得た競合作業対の集合を比較し、**対象競合が消えていること**と
**全体の対数が増えていないこと**の両方を要求する。

componentだけを見る判定は、切った先で新しい共有面を作る変換に対して無力である。三面分割は
共有surfaceを必ず作るので、この穴は理論上の懸念ではなく、本ADRが導入する変換そのものが踏む。

### 3. 並列度は実行段階数と最長経路で測る

同じ作業集合、同じ実行容量、同じ前提関係の下で、変換前後の最小実行段階数と最長実行経路長を
求め、いずれかが改善していることを要求する。両方が不変なら、その変換は並列化を解放していない。

競合辺の減少量そのものを採用条件にはしない。競合が減っても波数が変わらない切り方は存在し、
その場合に得られるのは変更費用だけである。

### 4. 改善が無い候補は棄却であって、失敗ではない

`parallelism_improved`を満たさない候補は`rejected`とし、理由を`no_parallelism_gain`として記録する。
変換器の欠陥ではなく、その切り方に便益が無いという判定である。同じconflictに対する別候補、または
意図的直列へ送る。

## Consequences

変換後の検証が重くなる。plan全体の再compileが要るため、componentごとの局所判定では済まない。
実行段階数の算出には作業集合と実行容量が要る——これは`runtime_plan.v1`が既に持っている。

採用される候補が減る。局所的に競合を消すだけの切り方、および波数を変えない切り方が落ちる。
これは意図した絞り込みである。**外部挙動を変えうる変更を、便益の証明なしに採用しない。**

## Open questions

1. **改善量の下限。** 実行段階数が1減れば足りるのか、変更費用との比を見るのか。明細書は変更費用
   （変更された資源、シンボル、インタフェース、状態移行、検査量）を候補評価の軸として挙げているが、
   採用の閾値は定めていない。実データが1件も無い段階で閾値を決めない。
2. **競合作業対の同一性。** plan revisionでtask_idが変わった場合の対の比較方法。現時点の変換は
   同一plan version内で完結するので問題にならないが、version barrierを跨ぐ比較には定義が要る。
