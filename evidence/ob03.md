# ob03: 調整方式の起票時宣言と未宣言の表出

## 何を作ったか

witnessが「全planの暗黙義務」だったため帰属が無く、`coverage: missing`の案内は文言まで正確
だったのに8件のToDo全部で素通りされた（前campaign room [96] #3）。是正は督促を強めることでは
なく**帰属を作る**ことである（オーナー裁定C①）。commit `3e2adb7` / `3201c77` / `448db12`。

### 1. 宣言はplanへ帰属するjournal event（`coordination_mode`）

taskにもPhaseにも属さない最初のkind。`task_id`も`phase_id`も持たない。**actorが「誰が選んだか」
を持つ**——ここを落とすとこの機構は「もう1つの督促」に戻る。`TODO_PLAN_SCOPED_EVENT_KINDS`
として型で括り、event validatorへplanLevel分岐を足した。

### 2. 置き場所は lifecycle journal と別のchain（設計差し替え）

**当初はlifecycle journal（`active.jsonl`）へ直接積んでいた。実storeへ書くとinstalled 0.47.0が
そのplanのjournal全体を`STORE_CORRUPT`にする**——`validateTodoEvent`は`TODO_EVENT_KINDS`を
exactで見るため。journalは`todo status`の正本なので、SessionStart hookを含む全消費者が落ちる。
**wireの版ズレではなくstore formatの前方非互換で、版を戻してもstoreは戻らない。**

ひなの [187][190] がnote側で見つけた逃げ道（旧readerは決まった名前のfileしか開かず、dirを
列挙しない）がjournal側でも成立することを実物で確認し（[194]・下記）、
`journal/plan-scoped.jsonl`へ分離した。**memoが名指しした設計（journal event・actor帰属・
hash chain）を1行も変えず、置き場所だけ変わる。**

- lifecycle journalと独立したsequenceとhash chain。genesisを持たない（planの存在はjournalが証明済み）
- `appendTodoEvent`はplan-scoped kindを別経路へ振り、**replay・snapshot・manifestへ触れない**
- **`member_heads`はtask chainだけを指し続ける**（みつき [195] の確定）。合成すると型も値域も
  同じまま意味だけずれ、消費者はexact検証を通してしまう
- 上限到達は`STORE_WRITE_REFUSED / plan_scoped_journal_segment_limit_exceeded`でtypedに止める。
  封緘機構は持たない（宣言はplanあたり数件の想定）——黙って捨てないため

### 3. CLIと案内

`lattice todo independence mode --plan <k> --set witness|conversation --reason <text>`
→ `lattice.todo_coordination_mode_result.v1`。resultは`journal_head_digest`ではなく
`plan_scoped_head_digest`を返す（lifecycleのheadを返すと「作業が進んだ」の意味が混ざる）。

案内（`todo-independence-guidance.mjs`）が方式で3分岐する:

| 状態 | code | next_action |
|---|---|---|
| 未宣言 | `coordination_mode_undeclared` | `declare_coordination_mode`（**どちらで行くか選べ**） |
| conversation | `coordination_conversation` | `none`（選択を尊重して督促しない） |
| witness | `independence_unrecorded`（従来） | `declare_witness_set_then_compile` |

既定は`witness`にして、宣言を渡さない既存呼び出しの挙動を変えない。

### 4. statusの`coordination`欄（v6）

```
coordination: [{plan_key, mode, declared_by:{host,session,agent}, declared_at, reason}]
```

**宣言済みのplanだけを列挙する。** 未宣言を`mode: null`で全plan出すと、plan数ぶん常に埋まって
読み飛ばされる列になる——前campaignで`audit_pending`の設計時に避けた形と同じ。未宣言は
「`member_heads`に居て`coordination`に居ない」で引ける。位置は`plan_notes`と`member_heads`の間
（room [152][158] の合意）。

### 5. `todo migrate`の`coordination_guidance`

起票直後は必ず未宣言なので、そこで選ぶ機会を案内する。`todo_migrate_result`はv2→v3
（ADR 0054どおりin-place追加はしない）。消費者はrepo内test 1件だけでdotagentsにpinは無い。


新規`test/todo-coordination-mode.test.mjs` 8件で固定したこと:

1. 宣言がstoreへ残り、**actorが帰属を持つ**
2. planへ帰属する——`task_id`も`phase_id`もnull、task状態は動かない
3. 宣言し直せる。**切り替えた人が帰属を持つ**（前の宣言者のままにすると誰が今の方式を選んだかが嘘になる）
4. **宣言はdispatchを変えない**——未宣言→conversation→witnessと動かしてもdispatch面がbyte一致
5. 案内が3分岐する（既定witnessも固定）
6. 方式は2値。壊れた宣言はstoreへ入らない（理由も必須）
7. statusの`coordination`欄は宣言済みだけを列挙し、上位キーの並びが合意どおり
8. **宣言はlifecycle journalへ混ざらない**——宣言後も`journal.activeBytes.length`が1バイトも
   増えず、journalのhead digestが変わらない

## 踏んだ罠

- **chainの起点が2種類ある。** `verifyLinearHashChain`は**sequence 0 ⟺ previous_digest null**を
  genesis束縛として検証する（journal系）。1起点で書いて`genesis_binding`で落ちた。
  note系は1起点（ひなの [206] の訂正）。**別chainを作る人は、その chain が属する側の起点規則に合わせる。**
- **`independence mode`の受理形はexact 8 argv。** `--set`の値は`TODO_COORDINATION_MODES`で
  argv解析の時点で絞る（storeまで持って行かない）。

## 正直に書くこと

**HEADの構文エラーを直したが、私の`3e2adb7`もHEADを壊れたまま残していた。**

`src/todo-contracts.mjs`の迷子の行（`catch`の中へ落ちた条件式）を直して出したが、その時点で
**`src/todo-cli.mjs`も別の迷子の行で壊れていた**（こはる [232] の実測）。私が確認したのは
`todo-contracts.mjs`単体の構文だけで、**HEAD tree全体を見ていない**。解消したのは次の
`3201c77`（file全体をcommitしたため結果的に直った）。

**「作業treeのgreen ≠ HEADのgreen」**が今日生まれた断層で、`npm run check`も`npm test`も
作業treeしか見ない。私はその断層を見つけた側でありながら、**自分の修正commitで同じ断層を
踏んでいた**。こはる [232] の手順（stageしたsnapshotを取り出して構文検査してからcommit）を
以後の作法とする。

## 申し送り

- **`coordination_mode`を実storeへ書かない（publish前）。** temp storeでのみ検証している。
  散文正本の「この campaign 自身は会話調整方式で走る」を実storeへ宣言したくなるが、
  **別chain化した今も、宣言を読む側（`member.coordination`）は新CLIにしか無い**ため、
  実運用へ載せるのはpublish後にする。
- ADR 0160へ要る2文はob07のnoteへ渡してある（前方非互換の告知・`member_heads`は
  task chainだけを指す）。**封緘の非対称**（coordination chainは封緘を持たず、note chainは持つ。
  申し送りは溜まるが宣言は溜まらない）も、みつき [207] の提案どおり1行あると次にchainを
  足す人の判断が速くなる。
