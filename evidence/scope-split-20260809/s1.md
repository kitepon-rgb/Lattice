# s1 観測: 宣言差分と scope_expanded

- 実施者: tsumugi（つむぎ）
- 日付: 2026-08-09

## 何を作ったか

independence compile が**前回 artifact と今回の宣言を突き合わせて、task 別の膨張を事実として記録する**。
artifact schema を **`lattice.todo_independence.v5`** へ上げ、`scope_expanded` を足した（`task_ids` と 1:1）。
**最初 v4 で出し、監査で前方互換の破壊が見つかって v5 へ上げ直した**（下の「監査で直した4件」④）。

```
task_id                   どの task か
compared_witness_digest   比較相手の witness_set_digest（比較できなければ null）
first_seen_path_count     その task を最初に見た時の宣言 path 数
path_count                今回の宣言 path 数
added_paths               前回から増えた path（昇順）
removed_paths             前回から減った path（昇順）
growth_events             宣言が増えた回数の累計
gate_shape                plan の hard_dependencies で入次数2以上か（合流点）
```

### 判断を入れていない

今日この campaign で、**1つの task（r2）に膨張が3種類同時に出た**:

```
上流由来    r1 の attach 契約が確定した結果、launch-seat が対象に入った
自変更由来  自分の変更で SKILL.md の起動 command が動かなくなり、直す必要が出た
見落とし由来 charter / setup / teardown に元から向きが埋まっていた
```

**機械にはこの3種を区別できない。** 装置が言えるのは「増えた」「何が増減した」「何回目か」
「合流点か」までで、**仕分けは AI がやる**（所有境界: 推定・判断を Lattice の中へ実装しない）。
だから `scope_expanded` に**閾値も勧告も分類も無い**。勧告は s2 の担当で、この記録の上に乗る。

### `removed_paths` は散文に無いが入れた

**増加だけを見ると「盛った」と「宣言をやり直した」が同じ顔になる。** r2 は増える一方だったが、
宣言を組み直す task では減る。増減を両方置かないと読み手が誤る——**これは私の判断**で、
room [1053] で先に出して異論が無かった。

### 「比較できなかった」を「膨張ゼロ」に化かさない

`compared_witness_digest` が null なのは **「まだ比べていない／比べられなかった」の印**である。
`added_paths: []` だけで表すと、**「比べて増えていない」と区別が付かない**。
比較不能は4つ: 初回・plan version 違い・topology 違い・旧 schema。
どれも初回として置き直し、**前回の `first_seen_path_count` を継がない**（継ぐと嘘の比率になる）。

## どう確かめたか

focused test `test/todo-scope-expansion.test.mjs`（新規）。**当初6件で出し、監査の指摘で3件足して最終9件**——
以下は**当初の6件**で、④以降で足した3件は「監査で直した4件」の節に書く。

```
① 初回は比較相手なしとして記録する（膨張ゼロと区別できる）
② 宣言が増えると added_paths と growth_events が動き、初回の数は保たれる
   ＋ **負の対照: 宣言が変わっていない task には何も出ない**
③ growth_events は膨張した回数だけ増える（同じ宣言を再 compile しても増えない）
④ 宣言が減ったら removed_paths に出て、growth_events は増えない
⑤ gate_shape は入次数2以上だけ true
⑥ 前回 artifact が比較不能（version 違い・topology 違い・旧 schema）なら比較相手なしとして扱う
```

### 負の対照（当初の3つ。最終形での再実測は末尾の「最終 gate」を見ること）

```
② removed_paths を出さない                     → 6中 1 fail
③ gate_shape を常に false                      → 6中 1 fail
復元後                                          → 6/6 green
```
**確かめずに出た green は、通っても意味を持たない。**

## schema を上げた影響（先に周知した）

`v3` → `v4` → **最終 `v5`** なので、**旧版 artifact は legacy marker として読まれ、その plan の
independence は `record_superseded` になる**。**各 plan で `todo independence compile` を
1回打てば戻る。** 影響は実測した:

```
active plan 総数                             41
再 compile が要る（現行版でない artifact 持ち）15（この実測時点。v5 化で v4 の4 plan も対象に加わる）
artifact をまだ持たない（未 compile）         26  ← 影響なし
うち今日の卓が動かしている plan                6
残り9本は今日触っていない過去 plan            ← **今すぐ打ち直す必要は無い**
```
**私は最初 room [1062] で「9 plan 前後」と概数で言った。数えたら15本だった。**
概数のまま残すと、次に読む人が「思ったより多い」で驚く——**今日この卓で何度もやられた形**である。
過去 plan 9本は**次にその plan を触る人が1回打てば戻る**し、それまでは `record_superseded` として
**「まだ判定していない」と loud に出る**。黙って壊れるのではない。

**別 artifact file に持つ案も検討したが採らなかった。** 二重管理になり、
artifact と記録が食い違った時に「どちらが正か」を消費者が判断することになる。
version bump は既存の作法（witness v1..v5・independence v2→v3）で、
読み口が legacy marker へ落とすので**壊れずに気づける**。

## 監査で直した4件（suzune・kanade・実コードで再現）

### ① 例外を握り潰していた（`todo-cli.mjs`）

```
before  try { previousArtifact = await readTodoIndependenceArtifact(...) } catch { previousArtifact = null }
```
`readTodoIndependenceArtifact` は**「欠落だけ null・旧版は legacy marker・壊れた記録は
`INDEPENDENCE_ARTIFACT_INVALID` で typed fail」を既に区別している。** そこへ catch を被せたので、
**corrupt / permission / I-O まで「初回」へ化けて、履歴を黙って切ったうえで新 artifact で上書きできた。**
catch を外した。**「読めなければ null」は正しかったが、「読めない」の中身を潰したのが誤り**である。

### ② subset 入替を「初回」へ偽装していた

witness は **wave 単位の subset** で書き出せる（私自身が `7a6a17f` でその生成器を置いた）。
A→B→A と入れ替わると直前 artifact に A が居ないので、今回を初回と置いてしまい、
**本当の初回宣言数と膨張回数が消えていた。** suzune が具体的な再現手順で示した。

**schema は上げずに直した。** `first_seen_path_count` と `growth_events` を **`number | null`** へ広げ、
**当初は**「既存の v4 artifact（数値）はそのまま有効なので churn を増やさない」と判断した——
**それが誤りで、④ で v5 へ上げ直した。**
```
初回（比較相手が無い）          compared_witness_digest = null    ＋ 数値
subset gap（相手はあるが不在）  compared_witness_digest = digest  ＋ **null**
```
**null は 0 ではなく「分からない」。** 装置が知らないことを 0 と書かない。

focused に1件足して 7/7 green。**負の対照**: subset gap の分岐を外すと 1 fail、戻すと 7/7。

### ③ null を後続へ伝播させていなかった（suzune [1173]）

`(prior?.growth_events ?? 0) + 1` なので、**一度 null になった累計が次の compile で 1 へ戻り、
「欠落前が分からない」を「1回膨張した」へ偽装していた。** null は伝播させる。
4回目の回帰 test を足した（A → B → A[gap] → A+1本 で null のまま）。
**直近の差分（`added_paths`）は言える**ので、**言えるものと言えないものを分けて出す。**
負の対照: 伝播を外すと 9中 1 fail。

### ④ 同じ版名で形を変えていた（suzune [1183]・kanade [1200]）——**今日の P0 と同型**

`first_seen_path_count` / `growth_events` を integer → nullable へ**v4 のまま**広げていた。
これは**「新 reader が旧 artifact を読める」後方互換しか満たさない。** 旧 v4 reader は
既に main・公開 daemon・実 artifact に居るので、**新しい null 入り artifact を読めない**——
**前方互換の破壊**であり、**今朝私が起こした P0 とまったく同じ形**である。

**実測で確かめた**（`ffe1d28`＝v4 時点を worktree に出し、その validator へ食わせた）:
```
① v4 reader × 現行 v4 artifact         true    正しい
② v4 reader × v5 artifact              false   legacy 読み口へ落ちる（設計どおり）
③ v4 reader × **同名 v4 で null 入り**  false   ← **同名変更が壊れる証拠**
```
`TODO_INDEPENDENCE_SCHEMA` を **v5** へ上げ、**v4 を legacy 集合へ**入れた。
**私は「既存 artifact が数値のままなら有効」で足りると判断したが、
見ていたのは片方向だけだった。** 版を上げないと、読む側が古い場所（公開 daemon）で必ず割れる。

**再 compile が要る plan がまた増える。** v4 まで進めた4 plan（redirect / carryover /
scope-split / viz）と、v3 のままの過去 plan は、いずれも `todo independence compile` 1回で戻る。
**今日2回目の版上げなので、これ以上は上げない形で設計する**——次に unknown 表現が要るなら、
**v5 の中で新しい欄を足すのではなく、最初から nullable で定義した欄を使う。**

## 最終 gate（**ここが唯一の最終結果。上の各節は経過であり、途中の数字は当時のもの**）

**上の節には、私が当時そう信じて書いた数字がそのまま残してある**（`exit=0`・「v4 起因は2本」・
「npm run check は走らせていない」など）。**そのいくつかは後で反証された。** 消さずに残すのは、
**誤測定→反証→最終実測**の経緯そのものが s1 の題材（宣言と実態のずれ）だからである。
**最終の事実は以下だけを読むこと。**

### 私の測定器が壊れていた（今日5回目・nagi [1215] が反証）

```bash
node --test "$f" >/dev/null 2>&1; printf "%-42s exit=%s\n" "$(basename $f)" "$?"
                                            ^^^^^^^^^^^^^^ ここで $? が上書きされる
```
**`$(basename …)` が先に実行されて `$?` を 0 にしてから、`$?` が展開される。**
実証: `false; printf "%s exit=%s" "$(basename /tmp/x)" "$?"` → `x exit=0`。
**この形で報告した「exit=0」は全部 `basename` の終了コード**だった。
——**rc は必ずコマンドの直後に変数へ取る**（`cmd; rc=$?`）。整形はその後にする。

### 正しい形で測り直した最終結果

```
私の schema 追従で壊した fixture   3本
  seam-proposal-cli               → 直して green
  todo-obligations-e2e            → 直して green
  todo-independence-contracts     → **projection helper へも注入していた**（projection は
                                     artifact ではないので scope_expanded を持たない）→ 戻して 19/19
私の schema 起因で**まだ赤**       3本
  seam-proposal / -contracts / -queries
  `independence_schema: 'lattice.todo_independence.v3'` 固定の fixture が現行定数と合わない。
  **nagi が s1 へ join して直す。** 私は s1 の witness へその3 test を writes/affected_tests として足す
私の起因ではない赤                14本（baseline `ffe1d28^` でも赤。抜き取り実測）
npm run check                     148 files passed（[1208] で実施済み。上の「走らせていない」は当時の記述）
```

**s1 が done になるのは、上の「まだ赤 3本」が green になってからである。**

## やっていないこと

- **閾値・勧告・分類は作っていない**（s2 の担当・散文どおり）。s1 は記録だけ
- `runtime-seam-resolve.mjs` の compile 呼び出しには `previousArtifact` を渡していない。
  seam の pre/post 比較は**別目的の compile** で、そこへ履歴を継ぐと膨張の回数が汚れる
- **`npm run check` / 全 test は走らせていない。** 共有 tree に他席の未 commit source
  （r1 の runtime 側）が在るためで、**私の変更だけを走らせた結果を上に書いた**。
  全体 gate は tree が落ち着いてから
