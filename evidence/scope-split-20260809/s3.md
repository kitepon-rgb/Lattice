# s3 `todo split` — 実装・検証証跡

## 結論

公開CLI `lattice todo split` から、既存ToDoを子ToDo群と残余ToDoへ分割する phase v7 revisionを生成・適用できるようにした。
子と残余には `parent_task_id` で元ToDoの系譜を残し、元ToDoの下流依存は残余へ付け替える。
source inventoryをまだ持たない旧planからの初回cutover、既存source refとの衝突、witness移行失敗も含め、
plan・source inventory・witnessを不整合な途中状態へ残さない。

## 実施

- 実装commit: `5ee9bb3`
- 監査修正commit: `0cb27ef`
- `src/todo-split.mjs`
  - 子ToDoと残余ToDo、依存付替え、`parent_task_id`系譜を持つphase v7 revisionを構成する。
  - source inventory未導入のpredecessorでは、既存全taskと新しい子・残余を同じcutover batchへ収める。
  - 既存taskのsource refを予約し、子・残余との衝突をapply前に拒否する。
  - sourceを持たない既存taskは`carry_reconciled_metadata`、runtime stateは`carry`として維持する。
- `src/todo-cli.mjs`
  - `todo split --plan <plan> --task <task> --input <json>`を公開した。
  - canonical witness bytesとdigest identityを先に検証し、witness移行を準備してからrevisionをapplyする。
  - apply後に失敗し得るwitness移行を廃し、失敗時にplan/source/witnessの一部だけが進む経路を塞いだ。
- `test/todo-split.test.mjs`
  - 公開CLIを通した実phase v7 applyを固定した。
  - source ref衝突と不正なwitness task参照の負例で、plan/source/witness bytesが全て不変であることを固定した。

## 監査で修復した欠陥

- 子のsource refが既存taskのsource refと衝突できた。
- phase v7 genesisで、source inventory cutover batchへ既存全taskを収めていなかった。
- revision apply後にwitness移行が失敗し、plan/sourceだけが進む余地があった。
- 実applyで、sourceを持たない既存taskのmetadata carryを明示しないとphase v7契約を通せなかった。

いずれも`0cb27ef`で修復し、正側の実applyと負側のbytes不変をfocused testで確認した。
