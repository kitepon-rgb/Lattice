# ob05: 並列候補の逐次判定を配線する

担当: ひなの / plan: machine-held-obligations / オーナー裁定C③

## 何を作ったか

`todo_status_result` v6 へ `parallel_candidates` 欄を足し、**「まだ判定していない ready」と
「判定済みの結果」を answerable にした**。理想の動き——AIがツリーから並列できそうな組を選ぶ→
その組だけ宣言して compile→機械が可否を返す→否なら次の候補へ——のうち、判定機械（compile）と
部分宣言の受理は既に在り、**足りなかったのは候補の提示と導線**だった。

```
parallel_candidates: [
  { plan_key, coverage,
    unjudged_task_ids,          ← readyかつ未判定。これが「次に宣言する候補」の母集合
    verified_parallel_groups,   ← 判定済みで並列可（2件以上の組だけ）
    serialize_pairs,            ← 判定済みで直列必須（理由つき）
    next_commands }             ← 非空
]
```

上位キーは exact 12、並びは `blocked` → `audit_pending` → `plan_notes` → `coordination` →
`parallel_candidates` → `member_heads`（3人合意・room [152][256]）。

## 設計判断

### 1. 判定ロジックを1行も書かない

載るのは `projectIndependenceFrontier`（`src/todo-independence.mjs:301`）が既に出している結果を
候補の視点で並べ直したものだけ。**並列できそうな組を選ぶのはAIの仕事**で、機械が持つのは
「まだ判定していない ready はこれ」「判定済みの結果はこれ」だけである
（AGENTS.md 所有境界: 推定・判断・文章生成を Lattice の中へ実装しない）。

### 2. 記録が無い plan を飛ばさない

既存の `independenceForGantt` は `artifact === null` の plan を `continue` で飛ばす。
**それはまさに「まだ誰も判定していない」＝この欄が最も要る状態**である。飛ばすと沈黙が不在に見える。

### 3. ready を1つも持たない plan は entry ごと出さない

3つの列が全部空の plan も出さない。こはるの `plan_notes`（note ゼロの plan は出さない）と
同じ判断で、**満杯で始まる欄にしない**——前 campaign の witness `coverage: missing` が
実際に「常に全部未宣言」で4人全員に読み飛ばされた。

### 4. `next_commands` を持たせる

欄だけ置いて閉じない。未判定が残るなら `independence compile`、済んでいるなら読み出し。
`audit_pending` が届いたのは欄＋次の一手の名指しだったから（room [164]）。

### 5. どちらの CLI にも属さない場所へ置く

`todo status` と `lattice status`／`session-context` の両方が使うので、新規
`src/todo-parallel-candidates.mjs`。git の読みは呼び出し側から渡す（`gitHead` /
`changedPathsSince`）——このmoduleがgitの呼び方を決めると、2つのCLIが持つ既存の作法を上書きする。

配線はこはるの型を踏襲: `projectTodoStatus` の第2引数へ必須で足し、**結果を外へ出す2箇所だけ**が
実際に読む。内部判定は `TODO_STATUS_DISPATCH_ONLY` の明示の空（room [208]）。

## 実装中に踏んだ穴（他人の test が捕まえた）

最初、ready が在れば必ず `gitHead` を引いていた。**commit の無い repo（初期化直後・test fixture）で
`INDEPENDENCE_BASE_UNRESOLVED / git_head_unresolved` に落ちる**。こはるの
`test/todo-status-plan-notes.test.mjs` が5件まとめて赤くなって見つかった。

**教訓**: **判定に使わない値の解決を、判定していない plan を見るために要求してはいけない。**
HEAD が要るのは鮮度（`stale` 判定）だけで、`coverage: missing` の plan には鮮度が無い。
直し方は project-cli と同じ `PLACEHOLDER_SHA`。

**私の test は構造的にこれを踏めなかった**——fixture が `gitHead` を stub していたため。
他人の test が実装の穴を捕まえたのは今日2件目（1件目はすずめが HEAD の構文エラーを踏んだ）。

## どう確認したか

新規 `test/todo-parallel-candidates.test.mjs`（4件）。

| test | 固定した事実 |
| --- | --- |
| 記録が無い plan を飛ばさない | `coverage: 'missing'` で ready 2件が `unjudged_task_ids` に出る。next_commands は compile |
| 判定が済むと候補が変わる | `verified` / 並列可の組 / next_commands は読み出しへ |
| 競合は要直列として理由つきで出る | 競合した組は並列 group に入らず `serialize_pairs` へ |
| **どの段階でも dispatch は1バイトも動かない** | 判定前後で `active_set`/`next_ready`/`blocked`/`dispatch_frontier` が byte 一致、`frontier_digest` も一致 |

4件目は vacuous 対策として、比較の前に `next_ready` が `['T1','T2']` であることをリテラルで固定している
（両側同時に壊れた時に通る形を避ける・room [46][48] と同じ）。

- status 面まとめて（ready-frontier / status / audit-pending-e2e / coordination-mode /
  status-plan-notes / parallel-candidates / dispatch-unjudged / status-audit-pending /
  independence-cli / plan-note）**66 pass / 0 fail**
- `npm run check` → 141 files / `npm run check:cli-surface` → 67 commands

  今日「作業treeの green ≠ HEAD の green」で事故を出したので、受入条件へ入れた
