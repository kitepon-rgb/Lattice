# ob08 dotagents側消費者をv6へ追従させる

作業対象は別repo `/Users/kite/Developer/dotagents`。Lattice repoのsrc・test・docsには1バイトも触っていない。

## 前提——待った理由

v6へ欄を足すtaskは**3つ**あった（ob02 `plan_notes`／ob03 `coordination`／ob05 `parallel_candidates`）。
dotagentsの3消費者はいずれもexact key検証なので、**和集合を知らないと書けない**。片方だけで追従すると、
残りが着地した瞬間に`invalid_envelope`で落ちる（前campaign ap08で実測した形）。

そしてob08には**hard_dependencyが1本も無い**。起票時点からreadyで、いつでも取れてしまう。
機械はこの順序を持っていなかったので、`todo note`でob02・ob03・ob05へ「欄の最終形が固まったら
ob08へ貼れ」を貼った（room [141]）。3本とも届いた。

## 実装

### 1. `lib/orchestrate/lattice-projection.mjs`

- `TODO_STATUS_SCHEMA`をv6へ。上位exact keyを**12**へ（`plan_notes`・`coordination`・
  `parallel_candidates`を`audit_pending`と`member_heads`の間へ、卓の合意順で）。
- entry validator 3本。特に:
  - `plan_notes`は`latest[0].event_digest === plan_note_head_digest`を**消費側でも確かめる**。
    ここを確かめないと「最新のnoteはどれか」を読む側が自分で決めることになる。
  - `coverage`の4値（`verified`／`stale`／`superseded`／`missing`）は**リテラルで焼く**。
    5値目が来たらそれはwire versionの変更として来るべきもので、黙って受理しない。

### 2. `lib/orchestrate/lattice-control-saga.mjs`

- 観測schemaをv6へ。`TODO_STATUS_KEYS`へ3欄、entry検証3本。
- **束縛照合は`{v4, v5, v6}`。過去版を消さない。** `external_source.contract_version`は
  束縛した時点のwire版を書き残した履歴であって、いま観測しているwire版ではない。
  同一視すると旧版時代に束縛した既存Controlが「束縛が1件も無い」で落ちる（前campaignで確立）。
- 工程3欄はsagaの選択・束縛へ**使わない**。工程に属する事実であってdispatchではない（ADR 0160）。
  ただし**素通しと無検証は別物**なので値域まで検証する。

### 3. `lib/lattice-hook.py`

- v6を受理。`STATUS_SCHEMAS_WITH_PROCESS_FIELDS`でkey-setを分岐し、entry validator 3本。
- **v1〜v5の受理は残した。** publishまでの移行窓でinstalled CLIは旧版を返し続けるので、
  exact pinにするとその間ずっと全projectの工程案内が消える。
- 依存件数・校正状態のschema分岐へv6を追加。

### 4. test・契約文書

- smokeの「未対応の将来版」代表を**v6→v7**へずらし、**v6の受理ケースを新設**（両hook）。
- `docs/factory-product-contracts.md`のstatus面wireをv6へ。消費者3つと、束縛照合が別軸である
  ことも明記。

### 5. anchor test（room [196]で すずめと約束した分）

`tests/orchestrate/lattice-control-saga.test.mjs`へ1件:

- 工程3欄が埋まっても返るactionがbaselineと`deepEqual`
- `member_heads`と`dispatch_frontier`が動かない
- 値域外（`mode: 'auto'`／`coverage: 'ready'`／headでない`latest[0]`）は`INVALID_OBSERVATION`

**生産側の anchor（すずめの `todo-dispatch-unjudged.test.mjs`）が「いま そうなっている」を、
これが「消費側の期待がそこにある」を固定する。** B'（別chain）なら構造上そうなるので今は自明だが、
**将来chainを合成する変更が入ってもdotagentsは落ちない**（型も値域も同じなので）。
生産側の構造が変わった時に消費側が気づく仕掛けが、これで1つ在る。

## 散文の宣言と実装がずれていた箇所——実物を読んで直した3件

room の宣言をそのまま焼いていたら、3件ともdotagents側の受理が落ちていた。

1. **`coverage`**: 宣言 [256] は `'ready'`、実装は `'verified'`。私が [258] で「`'ready'`を実物で
   見ていない」と確認を出した枠。**存在しない値だった。**
2. **`verified_parallel_groups.task_ids`**: 宣言は「2件以上」、実装は`length > 0`。
   **実装に合わせた**——1件のグループが出うるので、2件以上で焼くと落ちる。
3. **上位キー数**: [260] の本文は「exact 10」、列挙も実装も**12**。typoと判断して12で書いた。

**キー名だけでは validator は書けない。** 値域が要る、というのが ob08 側から見た教訓。

## 移行窓の既知の帰結

publishまでの間、`lattice-projection.mjs`と`lattice-control-saga.mjs`はinstalled CLI（v5）を
`version_mismatch`として拒否する。exact pinとdownstream先行protocol（ADR 0054）の組み合わせから
必然的に生じる窓で、typedかつfail-visibleなので沈黙failureではない。**hookだけは多版受理なので
この窓でも案内が出続ける。** 面によって版pinの方針を変えているのは意図である。
