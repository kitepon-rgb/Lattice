# ap04: lattice status の next_action を監査待ちへ向ける

## 何を作ったか

`lattice status --json` は全taskがdoneになると `next_action: {"reason":"no_ready_task"}` を返していた。
機械が「残作業なし」と答える限り、AIは正しくそれを信じて完了報告する。監査待ちが在る限りそう
答えないようにした。

`src/project-cli.mjs` の `resolveProjectState` の next_action 分岐へ、`todo.audit_pending.length > 0`
の枝を1つ足しただけである（ap03 の v5 で入った欄をそのまま読む）。

```js
: todo.audit_pending.length > 0
  ? { command: `lattice todo phase status --plan ${todo.audit_pending[0].plan_key}`, reason: 'audit_pending' }
  : { command: 'lattice todo status', reason: 'no_ready_task' };
```

守った制約:

- **優先順位は `active_run` > `next_ready` > `audit_pending` > なし。** ready frontier が在る間は
  ADR 0063 の並列開始コマンドが勝つ。ここを監査で上書きすると dispatch が再直列化する。
  監査待ちは `todo status` の `audit_pending` 欄に常在するので、順位を下げても消えない。
- **`state` は `ready` のまま変えていない。** 閉じた enum で host が分岐に使う。信号は `reason` が持つ。
- `project_status.v1` の bump 不要。キー追加は無く、`reason` は open string である
  （`src/project-cli.mjs:114-119` の validator が `typeof reason === 'string' && length > 0` しか要求しない）。
- 案内する command は **verbatim 実行可能で読み取り専用**の `todo phase status` にした。
  `phase review` は `--reason <text>` の placeholder を含み journal を書き換えるので置いていない。
  `todo phase status` の結果には既に両分岐の guidance が載っている。
- `runSessionContext` は両 result を埋め込むだけなので無改修。

## どう確認したか

新規 `test/project-status-audit-pending.test.mjs`（3 test）。すべて**実CLIをspawnした E2E** で、
`plan create` → `todo start/done` → `phase review/accept/close-unaudited` を実際に流している。

1. **優先順位**: 2件ready→`parallel_frontier_present` / T1だけdoneでphase-1がgate_readyになっても
   T2がreadyなら`next_ready_present`（監査で上書きしない）/ T2をstartすると`state:'active_run'`・
   `active_run_present`
2. **事故の現場**: T1もT2もdoneでready 0件の時、`reason:'audit_pending'`、
   command `lattice todo phase status --plan main`、`state` は `ready` のまま、`active_runs` は空。
   さらに案内された command を**そのまま実行して exit 0** を確認し、2回実行しても
   `todo status` の出力が1バイトも変わらない（読み取り専用である）ことを実測した
3. **戻り**: phase-1 を実 review→accept しても phase-2 が gate_ready で残る限り案内は消えず、
   phase-2 を close-unaudited した時点で `no_ready_task` へ戻る

途中で分かった実挙動を2つ、期待値の側を実物へ合わせた（実装は変えていない）:

- 後続Phaseは先行Phaseが accepted になるまで `locked` であり、`gate_ready` にはならない。
  よって全taskがdoneでも監査待ちは phase-1 だけになる。
- ready が2件ある間の `todo start` は ADR 0063 の `--parallel-frontier` 宣言を要求する
  （`PARALLEL_DISPATCH_REQUIRED`）。test の driver 側で宣言している。

## 申し送り

- 本repoの実storeでは監査待ちが0件なので、ここでも陽性は取れない。一時repoの実storeで
  陽性・陰性の両方を固定してある。受入ゲートの実測はこの工程の終端で1回だけ取れる。
- 焦点testを直接叩く時は `LATTICE_DASHBOARD_AUTOSTART=0` を付ける。
