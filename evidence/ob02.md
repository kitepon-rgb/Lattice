# ob02: plan単位noteをstatus面へ表出する（`todo_status_result` v6）

## 何を作ったか

ob01 が plan 単位 note の書き込みと配達（`todo start` の `note_context`）を作ったが、届くのは
**その plan の task へ着手した人**だけである。まだ誰も着手していない工程の義務は、`note list --plan`
を自発的に叩く動機が誰にも無いので、どこにも出ない。`src/todo-status.mjs` を v6 へ上げ、
plan 単位 note を一級の欄として返すようにした。

### wire schema

`TODO_STATUS_SCHEMA` を `lattice.todo_status_result.v5` → `v6`。ADR 0054・0063 の前例に従い、
既存 version への field in-place 追加はしていない。上位キーは exact 10キーで、`plan_notes` は
`audit_pending` と `member_heads` の間に入る:

```
schema, project_id, active_set, next_ready, dispatch_frontier, blocked,
audit_pending, plan_notes, member_heads, result_digest
```

### entry の形

```json
{"plan_key":"machine-held-obligations",
 "note_head_digest":"<64hex>",
 "count":2,
 "latest":[{"event_digest":"<64hex>","actor_agent":"koharu","recorded_at":"<utc>"}],
 "next_commands":["lattice todo note list --plan machine-held-obligations --json"]}
```

- **本文を1バイトも載せない。** note は自由記述 Markdown（`noteBodyBytes` 16KiB/件）で、
  `TODO_STATUS_CAPTURE_LIMIT`（64KiB）× plan 数と積を取ると、**note を書くほど status が
  `TODO_SCALE_EXCEEDED` で落ちる面**ができる。ADR 0159 Decision 2 が `auditGateGuidance()` の
  約330字の prose を `audit_pending` から落としたのと同じ判断である。要約や先頭160字の抜粋も
  検討して捨てた——bounded にしても plan 数に比例して積み上がる性質は同じで、
  「在ることは常に届く／中身は取りに行く」を厳密に守る方を選んだ。
- **`next_commands` を持つ。** 欄に出るだけでは読まれない。前 campaign で `audit_pending` が
  届いたのは、欄と**次の一手の名指し**を両方置いたからである（`todo phase status` は最初から
  監査待ちを出していたが、呼ぶ動機が無かった）。
- **`count` は current だけ。** 訂正（`supersedes`）された note を数えると、訂正するほど件数が
  増える。plan 単位で数える（task ごとに数えて合算すると task 数ぶん重複する）。
- **note を持たない plan は entry ごと出さない。** 全 plan を常に1行出すと、前 campaign の
  witness `coverage: missing` と同じ「満杯で始まるので読み飛ばされる欄」になる。
  `plan_notes: []` は「1件も無い」を積極的に述べている。

### plan noteはread modelに入っていない——第2入力を必須にした

`grep -n "notes\|Note" src/todo-store.mjs` → 0件。note の正本は
`.lattice/todo/notes/<plan>/active.jsonl` の別 chain（`readTodoNoteEvents`・async）で、
`projectTodoStatus(readModel)` は同期・store read model しか受け取らない。

そこで `projectTodoStatus(readModel, { planNotes })` の**第2引数を必須**にした。省略時に
空配列へ丸めると「note が無い」と「読まなかった」が同じ形になり、配線を1箇所忘れただけで
義務が静かに消える。それはこの欄が塞いでいる穴そのものである。素材は
`readTodoPlanNotesForStatus`（`src/todo-note-store.mjs` 新規）が作る。

### 内部呼び出しは`TODO_STATUS_DISPATCH_ONLY`（着手時の方針から1つ変えた点）

room [166] では「生産者6箇所すべてを明示的に配線する」と宣言したが、実装して**4箇所は
result を外へ出していない**ことが分かった:

| 呼び出し元 | result を出すか | 渡すもの |
|---|---|---|
| `src/todo-cli.mjs` `status()` | **出す**（`todo status --json`） | 実 note |
| `src/project-cli.mjs` `resolveProjectState` | **出す**（`session-context` の `todo`） | 実 note |
| `src/todo-cli.mjs` `startTask` | 出さない（ready 判定だけ） | `TODO_STATUS_DISPATCH_ONLY` |
| `src/todo-cli.mjs` independence 系 | 出さない（`active_set` だけ） | 同上 |
| `src/todo-cli.mjs` `independenceForGantt` | 出さない（`active_set` だけ） | 同上 |
| `bin/lattice-dashboard.mjs` | 出さない（生存判定だけ） | 同上 |

きっかけは実測で、6箇所すべてで note を読む形にしたら
`test/todo-note-gantt.test.mjs`「Ganttのnote chain破損は明示警告になりlive headも破損を反映する」が
赤くなった。**note chain の破損を明示警告として表出する契約が既に在る面を、私の fail closed が
二重に落としていた**（さらに dashboard は常駐 poll なので、note 破損が可視性ごと落とす）。
無名の `{ planNotes: [] }` ではなく名前付き定数にしたのは、**「うっかり空」と「意図した空」を
grep で区別できる形**にするためである。

### 読み取り失敗はfail closed（実際に読む2箇所）

`readTodoPlanNotesForStatus` は `readTodoNoteEvents` の typed error をそのまま通す。
warning へ逃がして `count: 0` に見せると、**壊れた義務記録が「義務なし」と同じ形**になる。

### コストは実測してから決めた

```
plan 34件（うちnote保有6件）の実store:
  readTodoStore              5224.1 ms   ← 支配項
  projectTodoStatus             3.3 ms
  全34 planのnote chain読み       7.0 ms   ← 追加コストの全量（store読みの0.13%）
  status_bytes                12579 B     ← 64KiB capture limitに対して19%
```
「軽いはず」で通さず測った上で、「plan note は要求時だけ読む」型の複雑さを設計から外した。

## どう確認したか

新規 `test/todo-status-plan-notes.test.mjs`（5 test・すべて `bin/lattice.mjs` 経由の実 CLI・実 store）。

1. plan note が `plan_notes` へ出て `next_commands` まで返る。**貼る前が空であることを先に固定**し、
   本文が載っていないこと・note を持たない plan が出ないことも同じ test で見る
2. task 単位 note は `plan_notes` を1件も動かさない
3. **dispatch 不変**: plan note を2件書いた前後で `active_set`／`next_ready`／`blocked`／
   `dispatch_frontier` が byte 等価、`frontier_digest` も個別に固定。vacuous 対策として
   「記録が実際に立ったこと」（`count === 2`）を先に assert し、`next_ready` はリテラルでも固定
4. `latest` は最大3件・新しい順、`count` は全件
5. **`session_context` の `todo` へそのまま届く**（ADR 0131 の合成面。追加の wire bump なし）

v5 を pin していた既存 test を v6 へ追従（同 commit）。`test/todo-ready-frontier.test.mjs` の
`GOLDEN_STATUS` バイト錨の変化は意図的な v6 bump によるもので、差分は `"plan_notes":[]` の挿入と
schema 文字列だけ。frontier 側は動いていない。`projectTodoStatus` の call site 28件も第2引数へ追従。


**`npm test` の赤3件はいずれも本 task 由来ではない。** 内訳:

- `案内はadvisoryと投影の両方へ同じ文言で載る` / `readyがあるplanだけ並列可否を要約し…`
  — ob03（`coordination_mode`）の未 commit の途中状態。room [171][172] で切り分け済み
- `実runで、宣言scope外の書き込みを走行中に観測して警報する` — 単独実行で pass（11.1s）。
  全体実行では 24.0s かかっており、4人同時作業の負荷で時間側へ寄った偽陽性

## 申し送り

- **`lattice status`（`project_status.v1`）には届かない。** `resolveProjectState` は `todo` を
  載せず `next_action` を導出するだけなので、plan note を出すには `project_status.v1` → v2 が
  要る＝dotagents の pin 対象が1本増える。ob02 の受入条件の外なので**やっていない**。
  `session_context` には届くので SessionStart 面は埋まっているが、`lattice status` だけを見る
  消費者には出ない。room [166] で論点として卓へ出した。
- **並行編集で hunk 単位の stage が要った。** `src/todo-contracts.mjs` と `src/todo-cli.mjs` は
  ob03（すずめ）の未 commit 変更と同居していた。**pathspec を明示しても file の中で混ざって
  いれば防げない**ので、自分の hunk だけを `git apply --cached` で stage した。
- **v6 の最終形はまだ確定していない。** `coordination`（ob03）と `parallel_candidates`（ob05）が
  この後 `plan_notes` と `member_heads` の間へ入る。ob08（dotagents 追従）には plan_notes の
  確定形を note で渡した（event_digest `ed2abab4…`）。**3つ揃うまで消費側は書けない。**
- **卓の `lattice` は global install 版**（`/opt/homebrew/lib/node_modules/@quolu/lattice`）で、
  この commit を含まない。plan note の配達を実測できるのは publish／install 後か、
  repo の `bin/lattice.mjs` 経由だけである。
