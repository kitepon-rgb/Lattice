# ap03: todo_status_result を v5 にして audit_pending 欄を足す

## 何を作ったか

`lattice todo status --json` の上位キーに監査欄が無く、全taskがdoneになると `next_ready` が空を返す。
機械が「残作業なし」と答える以上、AIは正しくそれを信じて完了報告する——これが終端監査失念の直接原因である。
`src/todo-status.mjs` を v5 へ上げ、監査待ちPhaseを一級の欄として返すようにした。

### wire schema

`TODO_STATUS_SCHEMA` を `lattice.todo_status_result.v4` → `v5`。ADR 0054・0063 の前例に従い、
既存versionへの field in-place 追加はしていない。上位キーは exact 9キーで、`audit_pending` は
`blocked` と `member_heads` の間に入る:

```
schema, project_id, active_set, next_ready, dispatch_frontier, blocked, audit_pending, member_heads, result_digest
```

### entry の形

みつきが room [14] で固定した消費側契約どおりの exact 6キー:

```json
{"plan_key":"main","phase_id":"terminal-audit","phase_status":"gate_ready","implicit":true,
 "required_evidence_slots":["terminal-audit"],
 "next_commands":["lattice todo phase review --plan main --phase terminal-audit --reason <text>",
                  "lattice todo phase close-unaudited --plan main --phase terminal-audit --reason <text>"]}
```

- task entry と紛れないよう `status` ではなく `phase_status`
- `next_commands` は非空必須。監査待ちなのに次の一手が空なら次アクション面として無意味である
- 並びは `plan_key` → `phase_id`

### 判定と定義をどこから取ったか（新しい定義を書いていない）

- 「監査待ちか」「次に打てるコマンド」は ひなのの `src/todo-audit-pending.mjs`
  （`AUDIT_PENDING_PHASE_STATUSES` / `isAuditPendingPhaseStatus` / `auditPendingNextCommands`）。
  状態集合を書き直していない。
- `required_evidence_slots` と `implicit` は ap01 の `todoPhaseDefinitions(member.plan)` と
  `isPhaselessTodoPlanSchema`。`plan.phases` を直接読んでいない（phase無しplanと synthetic model で落ちる）。

ひなのが room [22] で追加を予告した `auditPendingPhasesOf(readModel)` は**使っていない**。理由は
commit 独立性で、宣言時点で未commitだったため、依存すると私の commit 単体が赤くなり bisect が壊れる。
状態集合という本質的な重複は共有moduleで潰れており、残る差は `member.phases` を歩く3行だけである。
`collectAuditPending` は `buildTodoGraph` の member ループの中に置いた（design memo の指示どおり）。

### fail closed にした2点（フォールバックを置いていない）

- 導出ビュー `member.phases` に在って plan に定義が無い Phase → `TODO_STATUS_INVALID_INPUT /
  todo_status_phase_definition_missing`。slots を空へ丸めると「gateが何を要求するか」で嘘を吐く。
- Phase plan なのに `plan.phases` が配列でない → `todo_status_plan_phases_invalid`。
  素の TypeError で抜けさせない。

### dispatch へ触っていない

`isNodeReady` / `computeReadyFrontier` / `dispatchFrontier` / `frontier_digest` は無改変。
`audit_pending` は `member.phases` だけから作る別の列で、`nodes` / `incoming` へ流していない
（ADR 0062・ADR 0147裁定5）。

### 付随（版に依存する散文の修正）

`src/project-cli.mjs:337` と `src/todo-independence-contracts.mjs:475` のコメントが
「`todo_status_result.v4` は変更しない」と書いており、v5 bump で嘘になる。版非依存の表現へ直した。
別commit（cb7ae35）に分けてある。

## どう確認したか

新規 `test/todo-status-audit-pending.test.mjs`（6 test・すべて実storeで実測）。既存ファイルへ足さず
新設したのは、並行作業中の他メンバーと衝突しないため。

1. 全taskがdoneで `next_ready` が空になった時、`audit_pending` が1件出て次コマンドまで返る
   （**事故の現場そのもの**。実装前はここが完全な沈黙だった）
2. `phase_review` 後は `reviewing` として残り、`next_commands` が accept / reject へ変わる
3. `phase_accept` すると消える（accepted は待っていない）
4. `phase_close_unaudited` でも消える
5. Phase plan（v4）は `implicit:false` で plan 由来の slots（`heavy-check`）が出る。
   locked の後続Phaseは出ない
6. **dispatch 不変**: `phase_review` は task 状態を1つも動かさない。その前後で `next_ready`・
   `dispatch_frontier`（`frontier_digest` 含む）・`active_set`・`blocked` が byte 等価のまま、
   `audit_pending` の `phase_status` だけが変わる
7. pending task が残る間は Phase が active なので `audit_pending` は空

v4 を pin していた既存 test 5ファイルを v5 へ追従（commit 066fa3a）。
`test/todo-ready-frontier.test.mjs` の `GOLDEN_STATUS` バイト錨の変化は意図的な v5 bump によるもので、
差分は `"audit_pending":[]` の挿入と schema 文字列だけ。frontier 側は動いていない。

## 申し送り

- **本repoの実storeでは陽性が取れない。** 読んだ時点で監査待ちは0件で、
  `audit-pending-surface` 自身が gate_ready に入るまで陰性しか出ない。受入ゲートの
  「実storeで `lattice status --json` が監査待ちを指す」の実測機会は、この工程を閉じる直前の1回だけである。
  代わりに一時repoの実storeで陽性・陰性の両方を固定してある。
- **publish と global install は ap08 の dotagents 着地まで行わない。** dotagents が読むのは
  globally install された lattice CLI なので、v5 を先に出すと消費側が追従前の形で読む。
  加えて publish はオーナーの明示指示時だけ行う操作であり、ap03 の受入条件外である。本taskは commit まで。
- 焦点testを直接叩く時は `LATTICE_DASHBOARD_AUTOSTART=0` を付ける。付けないと `npm test` が渡している
  環境が無く、製品と無関係な `PROJECT_ROOT_CONFLICT` の赤が出る。
