# ob07: ADR 0160と公開契約をv6へ更新する

## 何を作ったか

### `docs/adr/0160-process-obligations-are-machine-held.md`（新規）

ADR 0159が直したのは「監査待ちが次アクション面に出ない」で、0160が直すのは**その一般形**である
——taskに属さない義務（順序制約・一度きりの観測・調整方式の選択）に、機械の中の置き場が無かった。
Contextには、この2 campaignで実際に観測された3件だけを書いた（散文にしか無かった順序制約、
帰属の無いwitnessが8件素通りした件、hard dependencyを持たないtaskが3つの和集合を待った件）。

Decisionは5つ:

1. **工程に属する義務はplan単位noteが持ち、次アクション面がその存在を告げる。** 別chain fileへ積む理由
   （混ぜると旧CLIでchain全体が`NOTE_LOG_CORRUPT`になり`todo start`が通らなくなる／storeは戻せない）、
   本文を載せない理由（capture limit×plan数で健全なstoreが落ちる）、`plan_note_head_digest`を
   `note_head_digest`と同名にしなかった理由（同名は同一性の主張で、型が同じdigestなので取り違えても
   exact validatorを通り抜ける）まで書いた。
2. **調整方式は起票後の明示選択で、選択に帰属が付く。** 宣言済みのplanだけを列挙する理由は
   「満杯で始まる欄は読み飛ばされる」——witness `coverage: missing`が実際にそうなった。
3. **未判定はdispatchを塞がない（Protected behavior）。** すずめがob04からnoteで渡した明文を**逐語で収録**し、
   anchor `test/todo-dispatch-unjudged.test.mjs`も名指しした。ADR 0159の非目的との関係も1文で述べた
   （監査状態と判定状態は別の状態で、どちらもdispatchへ流さないという同型の決定が2つ並ぶ。
   領域が重なっているのではない）。
4. **逐次判定は導線であって新しい判定ではない。** `parallel_candidates`を`dispatch_frontier`の外へ置く
   理由を、`dispatch_frontier`が`validateTodoStatusResult`の中で`next_ready`を引数に取って照合される
   唯一の欄である（＝「この欄は`next_ready`の関数である」が形に焼かれている）ことから書いた。
5. **v6へ上げ、downstream先行で公開する。** 上位キーはexact 12で、`plan_notes`・`coordination`・
   `parallel_candidates`がこの順で`audit_pending`と`member_heads`の間に入る。

Consequencesに**store formatの前方非互換**を独立の項として入れた（すずめのnoteの指定どおり）
——`coordination_mode`を1件でも書いたplanは旧CLIから読めなくなり、**wireは版を戻せば済むがstoreは戻らない**。
あわせて「**配達は読む側のCLIの版にも依存する**」を入れた（ひなの room [271]）。書けていても、
読む側がその版を持つまでは届かない。publishまでは散文が正でnoteが予備であり、順序が逆転するのはpublish後である。

非目的は裁定Bから直接来る「担当割りを機械化しない」（担当の死を検知できず永久ロックになる。
**記録と調整を同じ機構に混ぜない**）と、「宣言の中身を採点しない」「未判定・未宣言で何もblockしない」
「dispatch／readinessを変えない」。

未決3件はすべて発火条件つき（`check:open-questions`のgateを通る形）:
start済みへの押し出し経路が無い／`lattice status`にplan noteが出ない／
**常駐processの「生きているが応答できない」を登録簿が表せない**（今日dashboard daemonがpid・port・
descriptorすべて正常のままHTTPを返せなくなった実測から）。

  noteの節へplan note・`coordination`・`parallel_candidates`の説明を追記

  ——消費者から見て対処が違う（wireは追従、storeは不可逆）。noteのschema群の bumpも別項目

## どう確認したか

**共有作業treeでは測れなかった。** 4人が同じtreeで並行編集していて、`npm test`を回すと他メンバーの
実装途中（未commitのimport先が存在しない等）で20件以上が赤くなる。そこでHEADだけを測る形にした:

```
git worktree add --detach /tmp/verify HEAD
ln -s <repo>/node_modules /tmp/verify/node_modules
ln -s <repo>/sensor/dist  /tmp/verify/sensor/dist     ← 無いとnode-version-guardが
                                                         ERR_MODULE_NOT_FOUNDで全integrationを落とす
cd /tmp/verify        # 最終計測時はdocs commitが既にHEADに在るのでcopy不要
```

```
$ node scripts/verify-open-questions.mjs     open questions anchored: 29 / unanchored []
$ node scripts/check-syntax.mjs              syntax check passed: 141 files
$ node scripts/verify-cli-surface.mjs        cli surface verified: 67 commands
$ node scripts/verify-product-reachability.mjs  91 product modules / 33 declared research artifacts
$ node scripts/run-product-tests.mjs         tests 1407 / pass 1407 / fail 0
```

（測定の途中でHEADに赤が1件あった——`test/session-context.test.mjs`の
「壊れた記録は未判定へ丸めず理由を載せる」。ob05の着地由来で、`readTodoParallelCandidatesForStatus`が
壊れたindependence記録の例外を投げっぱなしにし、`resolveProjectState`の外側catchがstate全体を
`invalid`にしていた。**同じartifactを読む2つの面が、同じ壊れ方に違う答えを返していた。**
room [273] で全員宛に報告し、持ち主が修正した後に上の値を取り直している。）

## 申し送り

- **`package.json`のversionは0.47.0のまま。** CHANGELOGは0.48.0の節を持つが、版数の確定と
  `verify:release-commit`はreleaseの作業であり、ob07の受入条件（契約文書の版数が実装と一致）の外にある。
  前campaignも「v0.47.0: …releaseの版数と文書を確定する」を別commitで打っている。
- **契約文書にv6と書いてあることと、そのv6が届いていることは別である。** publish→global install→
  実機確認までがdotagents側（ob08）とreleaseの持ち物で、ob07が閉じられるのは文書までである。
- **dotagents側のLattice schema消費者一覧をADR／CHANGELOGへ書く案は採らなかった**（みつき room [248]）。
  下流の在庫を上流の製品文書へ書くと、下流が変わった時に上流が黙って古くなる（誰も更新の動機を持たない）。
  置き場所としてはdotagents側の契約文書が正しい。懸念自体（`lattice.hooks_status_result.v1`の消費者が
  居ることを知らずにpublishしうる）は実在するので、room [259] で置き場所ごと返した。
- **「検査が見ていない層だけが壊れる」はADRへ書かなかった。** 今日3つの形で出た（作業treeのgreen≠
  HEADのgreen／`node --check`はimport解決を見ない／file全体の置換は履歴を見ない）が、これは卓の
  作業手順の話であって製品のDecisionではない。**caveatが置き場所**で、すずめが引き取った（room [249]）。
