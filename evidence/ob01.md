# ob01: plan単位のnote書き込みを足す

担当: ひなの / plan: machine-held-obligations

## 何を作ったか

`todo note` の書き込みから `--task` 必須を外し、省略時を **plan 単位の note** として記録できるようにした。
あわせて**配達**まで実装した——書けるだけでは、前 campaign が直した穴の再生産になるため。

```
$ lattice todo note --plan <key> --message "<工程レベルの申し送り>"
   → scope: 'plan' の note が積まれる

$ lattice todo start --plan <key> --task <任意のtask>
   → note_context に plan note が載る（呼ぶ動機なしに届く）
```

### 確定した schema

| schema | 変更 |
| --- | --- |
| `lattice.todo_note_event.v1` | **触らない。** 既存 chain は hash 連鎖で固定済みで、task note の digest も動かさない |
| `lattice.todo_note_event.v2` | 新設。plan note 専用（`scope: 'plan'` ＋ `task_id: null`） |
| `lattice.todo_note_context.v2` | entry へ `scope`、`origin_task_id` を nullable、`full_history_command` を plan 形へ |
| `lattice.todo_note_append_result.v2` | `scope` 追加・`task_id` nullable |

**1本の chain に v1 と v2 が混ざる。** 投影（`noteProjectionEntry`）が両方を明示 `scope` へ正規化するので、
読み手は v1/v2 の区別を持たなくていい。

## 設計判断4件（room [138][150] で全員宛に宣言済み）

### 1. scope は enum フィールドで持つ。`task_id: null` だけで表さない

design memo は「`task_id` を nullable にする最小差分」を示唆していたが、実物を読むと通らない。
`validateTodoNoteEvent` は `exactRecord` 12キー固定で `task_id` が identifier 必須、
`noteContextEntry` も `origin_task_id` が identifier 必須である。

さらに **`task_id: null` を「plan 単位」と読むのは受け手側の解釈**になり、型で守れない
（room [134] みつき: exact validator は形しか見ないので、区別は型で表現しないと落ちない）。
投影の entry へ `scope: 'plan' | 'task'` を必須で持たせた。

### 2. `--phase` は作らない。plan 単位だけで閉じる

理由は memo の「需要が薄ければ」ではなく、**配達が無いから**。phase 単位 note の自然な配達点は
`audit_pending` entry で、それは ob02 の持ち物である。ここで書き込みだけ足すと、
**「書けるが誰も読まない面」を作る**——この campaign が直している当の穴である。

工程レベルの義務は plan note で書ける（「この plan の終端監査は一度しか観測機会が無い」も plan note）。

### 3. `full_history_command` を plan 形へ変える

`note_context` が plan note を載せる以上、`note list --plan <k> --task <id>` は**もう全部を取りに行けない**。
v2 では `lattice todo note list --plan <k> --json` にした。memo の「note_context の挙動を変えない」に
反するが、**変えないと full と名乗りながら plan note を落とす**。挙動不変より契約の正直さを取った。

### 4. `todo_note_append_result` も v2 へ（[138] 時点では挙げていなかった）

plan note には返せる `note_context` が無い——**どの task の context にも載るので、1つ選んで返すと嘘になる**。
`scope` を足して `task_id` を nullable にし、plan scope では `note_context: null` を返す。
**null は「無い」ではなく「1つに決められない」**の意味で、全部読む案内は `note list --plan <k>` が持つ。

## 実装した中身

- `src/todo-contracts.mjs` — v2 schema 定数、`validateTodoNoteEvent` の schema 分岐、
  `noteContextEntry` の `scope`、`full_history_command` の plan 形
- `src/todo-note-store.mjs` — `appendTodoNote` が `taskId: null` を受ける、
  `noteProjectionEntry` が `scope` を埋める、投影で **plan note は全 task の context へ載る**
  （task migration の対象外——特定 task に属さないので宛先を失わない）、
  訂正は scope を跨げない（`superseded_note_not_plan_scoped`）
- `src/todo-cli.mjs` — `note --plan <k> (--message|--input) [--supersedes]` の受理形、
  `appendNote` の plan scope 分岐
- `src/cli-help.mjs` — usage の `--task` を任意へ

## どう確認したか

新規 `test/todo-plan-note.test.mjs`（4件・全部 `bin/lattice.mjs` を spawn する E2E）。

| test | 固定した事実 |
| --- | --- |
| plan note は `--task` 無しで書け、scope 込みで list へ出る | 前 campaign で散文へ落ちた実例（「ap08 を ap03 より先に着地させる」）をそのまま fixture にした |
| **plan note は同じ plan の全 task の start へ、呼ぶ動機なしに届く** | T1・T2 の両方の `note_context` に出る。`scope: 'plan'` / `origin_task_id: null` / `full_history_command` が plan 形 |
| task note と plan note は同じ context に並び、scope で区別できる | T1 宛の note は T2 の context に出ない |
| 訂正は scope を跨げない | task note を plan note で訂正すると `superseded_note_not_plan_scoped` |

2つ目が受入条件の核心である。書けることだけを固定すると、届かない面を作っても緑になる。

- `LATTICE_DASHBOARD_AUTOSTART=0 node --test` で note 関連＋`note_context` を埋め込む消費面
  （`todo-note-gantt` / `todo-task-notes` / `todo-gantt-render`）まで含めて **59 pass / 0 fail**
- `npm run check` → `syntax check passed: 140 files`
- `npm run check:cli-surface` → `67 commands` / `undocumented: []` / `unexercised: []`

既存 test 4件の pin を新契約へ追従させた（`todo-note-contracts` の entry と `full_history_command`、
`todo-note-projection` の command、`todo-note-cli` の result schema）。挙動が変わったので pin も変わる。
