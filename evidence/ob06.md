# ob06: 工程の義務を機械が持つ面のE2E

## 何を作ったか

v6・plan note・調整方式の宣言・逐次判定は互いに絡む。面ごとの単体greenだけでは
「statusとnote listと独立性投影が同じ答えを指す」が守れない（前campaign ap06と同じ理屈）。
新規 `test/todo-obligations-e2e.test.mjs`（5件）。commit `ccf97b6`。

**実storeを実CLI（`bin/lattice.mjs`）で駆動する。** fixtureは一時repoで、`plan create` から
`todo note` / `todo independence mode` / `todo status` / `todo note list` まで全部CLI経由。

### (a) plan note書込 → statusの`plan_notes` → `note list` の3面一致

- note ゼロのplanは欄ごと出ない
- **statusのhead・note listのhead・書込結果のdigestが同じ1件を指す**
- **本文はstatusへ載っていない**（`JSON.stringify(plan_notes)` に本文が含まれないことを直接assert）。
  capture limitを踏まないための設計が実際に効いている
- **案内されたコマンドが実際に本文へ辿り着く**——`next_commands` の `note list --plan main` を
  実行した結果に本文が在る。案内が案内として成立していることまで見る

### (b) 未宣言 → 宣言 → 表出とguidanceが同時に変わる

- 未宣言のplanは `coordination` 欄へ出ない
- `todo start` のadvisoryが `coordination_mode_undeclared` / `declare_coordination_mode`
- 宣言後は欄に1件出て、`declared_by.agent` と `reason` が乗る
- **同じ操作でguidanceも変わる**——`coordination_conversation` / `next_action: none`。
  選択を尊重してwitnessの督促を出さない

### (c) 逐次判定: 未判定が候補として出て、判定が入ると候補から消える

- 記録が無いplanで `coverage: 'missing'`・`unjudged_task_ids: ['T1','T2']`・
  `next_commands` に `independence compile` が出る
- 判定記録を入れると `unjudged_task_ids` が空になり `verified_parallel_groups` が埋まる

### (d) note書込・方式宣言・判定記録のどれもdispatchを動かさない

3操作すべての後で `active_set`／`next_ready`／`blocked`／`dispatch_frontier` がbyte一致し、
`frontier_digest` も個別に一致する。**判定結果が「競合あり」でも塞がらない**（競合宣言つきの
記録で実測）。

vacuous対策として、**3操作が実際に効いていることを動いた側で確かめる**——`plan_notes` が1件、
`coordination` が1件、`unjudged_task_ids` が空。**不変だけを固定すると、3操作が全部無効でも緑になる。**

### (e) v6契約

- schema `lattice.todo_status_result.v6`、**上位キーexact 12**を順序込みでassert
- `result_digest` が自証する（再計算一致）＋ `validateTodoStatusResult` がtrue
- **v5形（3欄を落とした9キー）を拒否する。** digestを再計算し直しても false になる
- **欄を1つ落としただけでも落ちる**（exactの意味）

### ob04のanchorとの関係

memoは「(d)の不変anchorがob04のtestと同じ場所で固定される」を要求している。
**同じfileへ寄せず、相互参照で1箇所から辿れる形にした。**

- `test/todo-dispatch-unjudged.test.mjs`（ob04）: **projection層**で、記録の有無と競合宣言
- `test/todo-obligations-e2e.test.mjs` (d): **実CLI**で、note書込・方式宣言・判定記録

層が違うので統合すると片方のfixtureがもう片方に要らない重さを持ち込む。代わりに
**ob04のfile冒頭へ、両方を一緒に読むことと「欄を足す人は両方へ足す」を書いた**——
片方だけだと「その欄はdispatchを動かさない」が半分しか固定されない。

## 踏んだ罠（次にfixtureを組む人へ）

1. **commitが1つも無いrepoでは、判定記録が在ると `INDEPENDENCE_BASE_UNRESOLVED /
   git_head_unresolved` で status ごと落ちる。** 記録の鮮度判定に実HEADが要るため。
   fixtureは `git init` の後に**commitを1つ持つ**。
2. **`base_sha` を固定値にすると判定済みでも候補に残る。** 記録がstale扱いになるため、
   「判定が入ると候補から消える」が検証できない。**実HEADを読んで入れる。**

どちらも前campaignの申し送り（`future_clock_skew`・task形exact）と同じ種類で、
**実storeでしか出ない**。

## 観測（受入条件の外・room [269] へ報告済み）

**room の散文で読んでいたから付けられた**。機械へ移した情報が届かず、散文が働いた。

配達の穴の3件目（(1) 押し出しはstartの一度きり (2) 書いたものが残るか (3) **その CLI の版で
読めるか**）。**publish後に解消する**性質のもので、ob06の受入条件の外。ob07の未決節へ
広げるかは持ち主の判断として材料だけ渡した。
