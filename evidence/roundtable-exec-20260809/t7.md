## 受入 gate が見つけた4層の欠陥（この節が t7 の主産物）

**どれも unit test では緑のまま通り抜けていた。** 実 run でしか出ない。

| 層 | 欠陥 | 露出した run | 修正 |
|---|---|---|---|
| ② | `KNOWN_ADAPTERS` に `work-order` が無く `run start` が入口で弾く | accept-1 前 | `78ca6ce` |
| ③ | `.lattice/runtime/` が untracked で canonical clean にならない | accept-1 前 | peertable `7c5e422` |
| ④ | adapter 登録形が ADR 0126 Decision 2 違反（script を `binary_path` へ） | accept-1 | 再登録＋peertable `d5d484f` |
| ⑤ | 公開 CLI に dispatch 駆動経路が無い（scripted の file 名 gate） | accept-2 | `565239e` / `75dce35`（capabilities v2・ADR 0161） |
| ⑦ | supervisor→controller の dispatch request が固定5秒 | accept-3 | `f169a3b`（validated heartbeat で再arm） |
| ⑧ | CLI→supervisor の activation socket が固定5秒 | accept-4 | `a354738`（初回だけ timeout 0） |
| ⑨ | error schema が scripted 名 hard-code で真の error を潰す | accept-5 | `48bc09c`（既知2 schema を検証伝播） |
| ⑩ | dispatch 時に「全子孫が root と同一 PGID」を要求 | accept-6 | `67e31ee`（dispatch だけ緩和・barrier は strict 維持） |

### ⑤ が本丸だった（ADR は禁じていなかった）

`driveScriptedManagedEpoch`（`runtime-cli.mjs:843`）の呼び出しは2箇所とも
`isDistributedScriptedControllerActivation`（`:1199`）で守られ、**`adapter_kind === 'scripted'` かつ argv に
`lattice-scripted-adapter.mjs` を含む時だけ**駆動していた。ADR 0126 はこれを禁じておらず、**正しい形を
名指しした上で別裁定へ送っていた**（同 ADR:75-82）:
> file名で中核挙動を分岐させる形は恒久設計として弱い。**正しい形は `lattice.runtime_adapter_capabilities.v2`
> でcontrollerが初回駆動の受入を宣言し、supervisorが宣言だけを見て判断することである。**

卓はこの裁定を今行い、`host_driven_epoch` を **登録入力 v2/true と handshake v2/true の両方一致でのみ駆動**
（不一致・未知版は fail closed、adapter 名で分岐しない）とし、ADR 0161 で固定した。

### 隠蔽が層をなしていた

⑦⑧⑨は**すべて「本当の理由を隠す」種類の欠陥**だった。5秒 timeout が dispatch の待機を殺し（⑦）、
その上の5秒が activation の結果を殺し（⑧）、error schema の hard-code が中身を捨てていた（⑨）。
**1枚剥がすたびに、その下から本当の理由が出てきた。** akari [343] は⑧の修正前に「真の typed rejection が
隠れている」と予告し、実際にそうなった。

## 測定器についての記録（数字の意味を担保するため）

### 同じ `--version` で挙動が違う2つの CLI

```
$ lattice --version → 0.50.1      $ node bin/lattice.mjs --version → 0.50.1   ← 同じ
$ lattice run status --run …            → {"code":"INVALID_RUN_STORE"}
$ node bin/lattice.mjs run status --run … → 正常
```
global install は `work-order` を知らず、`readRunStore` の `KNOWN_ADAPTERS` 検査（`runtime-cli.mjs:583`）で
run store を不正と判定する。**版番号では見分けられない。** 監査は source tree の CLI で行うこと。

### pid 再認証が fail closed した（allowlist 形で書いていたから助かった）

残存 process を停止する前に `ps -o lstart=,args=` と descriptor の `process_start_identity` を照合したが、
**出力側だけ空白圧縮し、期待値（`Sun Aug  9`＝二連空白）を圧縮していなかった**ため同一 process が
「再認証NG」になった。**安全側に倒れたのは判定を allowlist 形（一致したら停止）で書いていたから**で、
denylist 形なら無関係 process を殺していた。以後の掃除では **argv の run dir 一致**まで照合条件へ入れた
（supervisor は複数 run で同名 process になるため）。

### 失敗 run の後始末

accept-2/3/4/5/6 はいずれも公開 CLI で終端できず、identity 再認証つきの手動回収を行った。
`pkill` は一度も使っていない。**最終確認: 孤児 supervisor 0件（親が独立に `reap-orphan-test-daemons.mjs`
で確認）**・worktree 撤去済み・spool 0 件・canonical clean。

### 私が出して撤回した誤り

1. **「epoch 駆動は前景 CLI に載っている」** → 実際は `runManagedSupervisorDaemon`（`runtime-cli.mjs:2022`）の
   内側（`:2528`）＝daemon 側。kanade [340]・akari [343] の指摘で確かめて訂正
2. **⑨で「terminal push が unsolicited になっている」** → コードで反証（work-order の dispatch は first report 後に
   1 response だけ返す）。真因は error schema の hard-code
3. **⑧で「order publish 時に即応答し worker identity は後から束縛」** → dispatch response v2 の
   `worker_process` 必須と「dispatch 時点で停止対象を名指し」（請求項9の土台）を壊すため不可
4. **field 名 `host_driven_initial_dispatch`** → 同じ predicate が recompile 後の epoch driver も守るため狭く誤記
5. **「`.lattice/runtime/` は gitignore 済み」** → 確かめずに書いた誤り（suzune [194] の指摘）

**受入報告に間違った因果を残す方が悪い**ので、訂正ごと残す。

### 自分の実装の欠陥を1つ見つけた（t4 run-bridge）

accept-5 で席の `[受諾]`／`[完了]` を bridge が握り潰した。`findEntry` が (席, todo_id) で配車記録を引く際に

t4 は done 済みのため `lattice todo note`（t4 sequence 4）と本証跡に残す。

## 申し送り（t7 では直さない・後続 ToDo 候補）

1. **⑥ 動いている repo の run は公開 CLI で終端できない。** `close`/`resume` は `STALE_BASE`
   （HEAD == base_sha 要求）、`abandon` は heartbeat 失効後に `CONTROLLER_HEARTBEAT_EXPIRED`。
   結果 supervisor と controller が公開面から止められない常駐として残る。**②は commit 凍結で測れるため
   t7 へは足さない**という卓の裁定（kanade [273]・akari [274]・suzune [275]）に従う
2. **待機が外から見えない。** ⑦⑧の修正で「validated heartbeat 中は待つ」「初回 activation は最終結果まで待つ」
   になったが、**heartbeat が証明するのは controller の生存であって配車の進行ではない**。bridge が落ちる／席が
   配車を読み落とすと `run activate` は無言で待ち続ける。要求は「止めること」ではなく
   **「待っていることが別 process から見えること」**（例: `run status` に dispatch 応答待ちが出る）
3. **spool の order/report が run を跨いで残る。** bridge は掃除しない設計（controller が次の order 発行前に
   stale report を消す）なので、close 後も残り溜まる
4. **`run request synthesize` は `executor_capability.adapters: ['todo-independence']` 固定**なので
   `run start` へ直接渡せない。面の性質であり破断ではないが、対象 adapter を選べる形にするかは別論点
5. **t20 publish 向け**: work-order 入りの run store は旧 install から読めず、理由が `INVALID_RUN_STORE`
   としか出ない
