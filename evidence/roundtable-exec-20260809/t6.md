# t6 setup拡張（peertable・越境）

## 実装

- Lattice併用modeのsetup開始時に、公開CLIと同梱
  `lattice-work-order-adapter.mjs` を解決し、実行不能ならprojectを書き換える前に止める。
  通常はglobal installされた`lattice`のcanonical pathから同じ`bin/`のadapterを導出する。
  release前のsource tree実測用に限り、`LATTICE_CLI`と
  `LATTICE_WORK_ORDER_ADAPTER_BINARY`で同じtreeのbinを明示できる。
- runtime configを `.lattice/runtime/work-order-adapter/config.json`、spoolを
  `.lattice/runtime/work-order-adapter/spool/{orders,reports}` に作成した。
  configを`.team/`へ置かずregistryと寿命を揃えたので、archive teardown後に
  descriptorだけが残ってconfig参照が壊れる形を作らない。
- exactな`lattice.runtime_adapter_registration_input.v1`を生成し、project rootで
  `lattice run adapter register --input`を実行してadapter kind `work-order`を登録する。
- `setup-state.json`へ`work_order_adapter`と`work_order_spool_ref`を追加した。
  単独円卓では`false`と空文字で、Lattice runtime資産を作らない。

## 検証

1. 負のcontrol: commit前の`skill/scripts/setup.sh`を`git archive HEAD`から取り出し、
   使い捨てgit projectでLattice併用setupを実行した。その後の
   `lattice run adapter list --json`は`adapters: []`、registry fileなしだった。
2. 正のcontrol: `/tmp/peertable-t6.qKR1if`で、Lattice source treeの公開CLIと
   adapter binaryを上記envへ明示して変更後setupを実行した。
   register結果は`schema=lattice.runtime_adapter_register_result.v1`、
   `outcome=created`、`adapter_kind=work-order`。
3. 同projectの`lattice run adapter list --json`はadapter 1件を返し、
   `launch_kind=host_binary`、binary path、空argv、
   `config_ref=.lattice/runtime/work-order-adapter/config.json`がdescriptorへ束縛された。
4. configは`schema=lattice.work_order_adapter_config.v1`とcanonical absolute
   `spool_dir`のexact 2 field。`orders`と`reports`はいずれもmode `0700`。
   setup stateは`work_order_adapter=true`とrepo-relative spool refを返した。
5. 単独円卓smoke `/tmp/peertable-t6-standalone.aemX46`はsetup成功、
   `mode=standalone`、`work_order_adapter=false`、spool ref空、`.lattice`なし。
6. `bash -n skill/scripts/setup.sh`、`git diff --check -- skill/scripts/setup.sh`はgreen。

## 監査で見てほしい点

- registryの`config_digest`へ束縛されるconfigとspoolが`.lattice/runtime/`にあり、
  ephemeralな`.team/`削除で壊れないこと。
- project外binaryやsymlinkを登録入力へ流さず、canonical executable pathを渡すこと。
- Lattice併用modeだけがadapter登録を行い、単独円卓の従来経路へLattice依存を持ち込まないこと。
- 既存registryでは公開CLIのreplace semanticsを使うため、別adapter entryを消さないこと。
