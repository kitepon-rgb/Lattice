# t14 実行時の線変更観測（Lattice）

- 実施者: akari（あかり）
- 日付: 2026-08-09

## 実装

- `detectCheckpointFindings` と `classifyObservedDiff` が、共有helperを使わず独立に
  boundary manifestの`lines`を読み、観測diffがanchor pathへ触れた時に
  `observed_line_change`を再導出するようにした。
- findingはpath findingへ偽装せず、exactな資源型
  `{ kind: "observed_line_change", todo_ids, resource_id: line_id }` とした。
  symbol anchorは計画どおり宣言済み`path`で近似する。
- 観測task自身が同じ`line_id`を`writes`宣言している時はfindingを抑止する。
  宣言していないtaskが線へ触れた時だけ、同時対象のreaderを`todo_ids`へ含める。
  running/relevant集合外のreaderは含めない。
- `classifyCheckpointObservation`からproducerへmanifestsを渡し、idempotence keyへ
  `resource_id`を加えた。同じtask組でも別line_idのfindingを取り落とさない。
- terminal supervisor経路でもline findingをactionableにし、candidateを
  `path: null / resource_id: line_id`として既存のfinding→conflict→holdへ運ぶ。
- `observed_line_change`はclosed runtime conflict kindへ追加した。資源型なので既存の
  severability判定は`serial`となり、seam変換へ誤って流れない。

## 正負の検証

新規`test/runtime-line-observation.test.mjs`で次を固定した。

1. path anchorとsymbol anchorの両方へ触れても、producer/verifierが独立に
   同じ1件のline findingを返す。
2. 同じline_idのwriter宣言を観測taskへ足すと、両実装ともfindingを出さない。
3. irrelevant readerはfindingへ入らない。
4. `conflict_found → intake_frozen → recomputeHoldDecision`でobserverとreaderの
   両方が`affected_closure`理由のholdへ入る。
5. 資源型candidateが公開validatorを通り、severabilityが`serial`になる。
6. 同じtask組の既存line findingがあっても、新しいline_idは別findingとして残る。
