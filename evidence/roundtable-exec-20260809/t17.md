# t17 run landing

## 作ったもの

- 公開CLI `lattice run landing --run <ref>` を追加した。
- accepted receipt の `checkpoint_digest` と、同じTODOで受理前に観測された
  `checkpoint_observed.diff.head_sha` をexactに束縛する。
- 各receipt HEADについて、remote既定branchへの
  `git merge-base --is-ancestor <head_sha> <default_branch_ref>` をread-onlyに実行する。
- repository単位で `git rev-list --count @{push}..HEAD` を読み、upstreamが無い場合は
  `push_state: "no_upstream"`、`unpushed_commits: null` として明示する。
- 出力は `lattice.run_landing_report.v1`。未着地・upstream無し・既定branch未解決も
  状態値として返し、exit 0を維持する。
- `run close` の `landing` fieldへ同じreportを同梱した。判定はCLI層だけに置き、
  runtime engineへgit依存を入れていない。
- CLI helpへ正規構文を追加した。

黒箱testは一時bare remoteとlinked worktreeを作り、次を実gitで確認した。

1. receipt HEADがremote既定branchに無い: `landed:false`、exit 0
2. canonical mainへfast-forwardしたが未push: `landed:false`、`unpushed_commits:1`
3. push後: `landed:true`、`unpushed_commits:0`
4. upstream解除後: `push_state:no_upstream`、`unpushed_commits:null`、exit 0
5. `run close`出力の`landing`が単独commandのreportと一致
6. command前後でrun store全regular fileのbytesが一致（read-only）
7. `run landing --help`を含む公開help契約
8. 同TODO・別digest、別TODO・同digest、受理後の同TODO・同digestをdecoyとして置き、
   3つのexact-bind predicateを1つずつ外すと必ず誤ったbase HEADを選ぶ負の対照
9. `accepted_receipts[]`を`receipt_id`込みのexact objectで照合
10. exact checkpointを解決できない時の`head_unavailable`と、remote既定branchを
    解決できない時の`default_branch_state:unresolved`／`default_branch_unresolved`をexit 0で実測

### 保存済み実run

`t7-accept-7`を新しい公開CLIで再観測した。

```json
{"schema":"lattice.run_landing_report.v1","run_id":"t7-accept-7","landed":false,"accepted_receipts":[{"todo_id":"t7probe","head_sha":"67e31ee7df49d80f9584208b329d782c8a308b62","landing_state":"not_landed","landed":false}],"repository":{"default_branch_state":"resolved","default_branch_ref":"refs/remotes/origin/main","push_state":"tracked","push_ref":"refs/remotes/origin/main","unpushed_commits":20}}
```

この実runではreceipt記録が先、terminal checkpointが後、receipt acceptedが最後だった。
実装は順序を決め打ちせず、accepted sequenceより前にある同TODO・同checkpoint digestの観測へ束縛する。

## 監査で見てほしい点

1. receipt→checkpoint→head SHAのexact bindが、別TODO・別checkpointを拾わないこと。
2. `landed`とrepo単位の未push本数を二重表現として混同していないこと。
3. 単独`run landing`と`run close.landing`が同じreportになり、run storeへ書かないこと。
4. `no_upstream`と既定branch未解決を成功へ丸めず、機械可読な状態値で分けていること。

## 監査補修

kanadeの独立監査 [484][485] で、実装コードに追加欠陥は無い一方、初回fixtureは正しいcheckpointが
1件だけでexact bindの3条件を落とした欠陥版もgreenになると判明した。上記8〜10を追加し、
focused testを11/11 green、`npm run check`を145 files greenで再確認した。
