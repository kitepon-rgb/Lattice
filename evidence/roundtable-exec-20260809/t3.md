## 何を作ったか

`lattice run request synthesize --witness <witness-set.json> --base-sha <sha> --id <request-id>`。
既在の `synthesizeWitnessRunRequest`（`src/todo-independence-contracts.mjs:135`）を公開面へ露出する
read-only surface で、stdout へ `lattice.run_request.v5` を1行返す。

**これは compile／independence 用の request である。`run start` の入力ではない。**
`synthesizeWitnessRunRequest` は `executor_capability.adapters` を `['todo-independence']` 固定で組む
既存契約なので、`run start` の「request の executor_capability に含まれない adapter」検査
（`src/runtime-cli.mjs:1211-1213`）に当たる。2026-08-09 の t7 実測で判明し、初版の証跡が
「`run start` へ渡せる run request」と書いていたのを訂正した——**面の挙動は設計メモどおり（既在関数の
露出）で、誤っていたのは説明の方である**（`lattice todo note` sequence 3 にも記録）。
`run start` 用の request が要る場合は、公開 `run_request` 契約から目的の adapter を宣言して組む。

設計メモどおり「露出するだけ」に留め、**判定を新しく持たない**:

- witness set の検査は `explainTodoWitnessSet` が単一の正本。CLI は理由（`reason`）と pointer を
  そのまま `lattice.cli_error.v2` の detail へ載せる
- 生成した request は `explainRunRequest` で自己検査してから出す。**自分の生成物が契約を満たさないなら
  装置の不具合**なので、黙って出さず `CONTRACT_VIOLATION` で止める

## 決めたこと（公開面なので記録する）

### 1. request id の旗は `--request-id` ではなく `--id`

`runRuntimeCli` の入口（`src/runtime-cli.mjs:3951-3960`）は、**末尾2引数が `--request-id <x>` の形なら
どの command でも先に横取りし**、run mutation 以外なら `INVALID_REQUEST_ID` で落とす。これは
idempotency key のための予約語である。同じ綴りを synthesize の「生成する request の id」に流用すると、
正しく書いたつもりの人が理由の分からない拒否に当たる。**同じ綴りへ2つの意味を持たせない**方を選んだ。

この振る舞いは test で固定した（末尾 `--request-id` は今後も拒否され続ける）。将来 `--request-id` を
使いたくなったら、入口の予約を先に解く必要がある——その判断はこの task の外である。

### 2. base sha を推測しない

`--base-sha HEAD` は typed に拒否する（`INVALID_BASE_SHA`）。CLI が HEAD を黙って採ると、
**「撮ったつもりの base と違う木」で run が始まる**。どの base に対する計画なのかは装置が知らないので、
呼び手に言わせる。

## 見てほしい点（監査依頼）

1. **`--id` という名前の是非。** 公開面なので後から変えにくい。`--request-id` の予約を解く方が筋が良い、
   という判断なら今のうちに言ってほしい

   この面が落とす経路が無いかを見てほしい
3. **usage 違反の形が既存 surface と揃っているか**（exit 2・stdout 空・stderr 1行）。
