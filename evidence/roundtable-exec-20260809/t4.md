## 何を作ったか

`skill/scripts/run-bridge.mjs`（新規・非AI常駐）。役割は4つだけ:

1. `<spool>/orders/<packet_digest>.json`（Lattice が書く）を2秒ごとに走査する
2. 空いている席を選び、**その席宛に work order を room へ投稿する**（＋`[配車] tN → 席` を全員宛へ）
3. 席の `[受諾]` / `[辞退]` / `[完了]` を room の SSE で拾う
4. `<spool>/reports/<packet_digest>.json` へ `working` / `done` を書く

**席へは1バイトも送らない。** 配車は room 経由で届き、起こすのは既存の経路（Claude 席は channels、
Codex 席は wakeup-bridge）の仕事とした。tmux への注入を bridge が二重に持たない。

生死は ADR 0157 の作法（pid 記録 `.team/run-bridge.json`・起動時に前の記録を掃除・`--stop` は
SIGTERM→SIGKILL・止まらなければ typed error で非ゼロ終了）。`teardown.sh` に停止段を足した
（**止め残すと、卓が無いのに次の run の order を拾って配車を投稿する常駐になる**）。

### 設計判断（room [他席と合意済みの前提の上で私が決めた点]）

- **配車を「端末への注入」でなく「room への投稿」にした。** 当初 t5 の文書は端末注入と書いていたが、
  複数行を tmux へ送ると1行ごとに送信される問題があり、bracketed paste へ寄せると席の CLI 実装依存に
  なる。room 投稿なら**既に proven な経路**（wakeup-bridge / channels）に乗り、席は spool 非接触のまま、
  卓のログにも配車が残る。member.md の「届き方」の記述は次項の申し送りとして残す
- **辞退→再配車を t4 に含めた。** t8 の範囲だが、含めないと Wave 1 で1席が辞退した瞬間に
  **誰も配車されず黙って止まる**。含めたのは「別の席へ配り直す」だけで、**busy 判定による idle 選定と
  `run observe` polling の room 可視化は t8 に残している**
- **SSE の頭出しが済むまで配車しない。** 返事を聞けない状態で配車すると、直後の `[受諾]` を既読として
  捨てる。これは実測で踏んだ（下記②）

## どう確認したか

### ① canonical JSON が Lattice と1バイト一致するか

report は controller が `bytes === canonicalizeArtifact(report) + '\n'` で突き合わせる。別 repo なので
Lattice の実装を import できず、bridge 側に同型の実装を持っている。**推測で書かず、実物と突き合わせた**:

| 入力 | 結果 |
|---|---|
| `run_work_report.v1`（working / done の2形） | **byte 一致** |
| 入れ子＋非ASCII＋配列＋null の混合 | **byte 一致** |

### ② 一気通貫（偽 room server ＋ 実 tmux 席2つ ＋ 実 bridge ＋ 実 Lattice controller）

`spawnWorkOrderWorker` を実物で呼び、席は実 tmux session（pane の shell の子に独立 process group の
node を置いた＝実席と同じ形）。

```
席: pane_pid=[1082,1091] group leader=[1110,1111]
① 配車: room へ出た
② 注入文の7項目: order と一致（worktree / base_sha / scope_writes / verifier_refs /
                              forbidden_operations / packet_digest）
③ 受諾前の report: 無い（正）
③b 辞退→再配車: probeseat → probeseat2
③c 辞退後の report: 無い（正）
④ 受諾後の binding: pid=1111 pgid=1111 membership=dynamic_group
⑤ report の mode: 600
⑥ Lattice が撮った observed diff: [{"path":"src/a.mjs","change":"modified"}]
```

`pid=1111` は**受諾した席の process group leader**であり、pane の shell ではない。
Lattice 側は `dynamic_group` として受理し、席が worktree へ書いた変更を**独立に**観測して
terminal receipt を組んだ。

**この過程で自分の測定器の不備を1つ、実装の不備を1つ見つけた**:
- 偽 room server が SSE の header を接続直後に flush していなかった（本物は心拍を流す）。
  bridge は正しく待っていただけで、**偽 server の不備**。`: connected` と ping を足して解消
- **実装の不備**: 頭出し（`primed`）より先に order 走査が走り、配車が「既読の境界」を作る前に出ていた。
  この順序だと受諾を捨てうる。`scanOrders` の先頭に `if (!primed) return` を足した

### ③ 停止（teardown が確実に止められるか）

```
① 起動後の pid 記録: ある
② 二重起動後の旧process: 止まっている（正）
③ --stop 後のprocess: 止まっている（正）
④ --stop 後の pid 記録: 消えている（正）
⑤ 記録が無い状態での --stop: exit 0（teardown を止めない・正）
```

⑤が要るのは、teardown.sh が `set -e` の下で走るためである（非ゼロで落とすと以降の撤去段が全部飛ぶ）。

## 見てほしい点（監査依頼）

1. **配車を room 投稿にした判断。** 席が room を読み落とすと配車が届かないままになる（端末注入なら
   届いたことが目に見える）。既存の起床経路に任せる設計が妥当か、別の目で見てほしい
2. **canonical 実装の二重持ち。** 別 repo なので同型実装が2つある。byte 一致は確認したが、Lattice 側が
   canonical 形を変えたら bridge は静かに壊れる（controller が typed reject するので黙ってはいないが、
   壊れる）。この結合をどう扱うかは設計判断が要る
3. **②の probe は偽 room server を使っている。** 本物の `room/server.mjs` との差（心拍周期・
   `?since=` の意味・system 発言）で挙動が変わる余地がある。実 room での一気通貫は t7 の範囲だと
   思っているが、t7 の前に見ておくべき差があるなら指摘してほしい
