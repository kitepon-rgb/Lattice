# t18 teardownのrun landing監査

## 作ったもの

- Peertable `5ec6ad1` で、teardownがrun-bridge停止後・`.lattice/runtime`削除前に
  setup時のwork-order spoolからmanaged runを列挙し、実
  `lattice run landing --run <repo-relative-ref>` を読むようにした。
- landing reportはJSONを欠落なく表示する。`landed:false`、未push commit、
  upstream無しは監査結果なのでteardownを失敗させない。一方、CLI不在・不正ref・
  landing command失敗は`miss`として最終exitを非0にする。
- `skill/SKILL.md`へcloseとlandingの区別、親監査で見る値、source-tree検証では
  `LATTICE_CLI`を明示する契約を追記した。
- `experiments/teardown-landing-repro.mjs`を追加し、保存済みclosed runを使った
  実CLI・実teardownの回帰を固定した。

## 検証

### 境界

- combined witnessはt11とt18をactiveとして現HEAD `64ccf75`へcompile済み。
- `lattice todo independence --plan roundtable-exec-20260809 --json`:
  coverage=`verified`、compiled/current=`64ccf75`、uncovered=0、drift=`null`、conflict=0。
- PeertableにはLattice sensor indexが無いため、この小さな対象限定変更のための
  新規初期化は行っていない。

### focused test

```text
$ bash -n skill/scripts/teardown.sh
$ node --check experiments/teardown-landing-repro.mjs
$ node experiments/teardown-landing-repro.mjs /Users/kite/Developer/Lattice
OK teardown landing: landed=false unpushed_commits=26 exit=0
$ PEERTABLE_URL= node room/client.mjs diagnostics --json
overall=ready; version_consistency/bin_integrity/node_runtime/skill_bundle=pass
$ git diff --check
exit 0
```

fixtureは保存済みclosed run `t7-accept-7`のstoreを使い捨てgit repoへ複製し、
remote既定branchをaccepted receiptの親へ固定した。これによりclose済みだが未pushの
境界を再現し、teardown全体がexit 0のまま`landed:false`と未push26本を表示すること、
run storeの`events.json` bytesが不変なこと、停止→landing→runtime削除の順を確認した。

補修前teardownをHEADから取り出す負の対照は、teardown自体はexit 0でもlanding reportが
無いため実験assertで失敗した。測定器が実装差を検出することを確認済み。

既存`experiments/teardown-silence-repro.sh`は4/4失敗した。原因はdecision 61後も
default archiveで`.lattice/`削除を期待する旧assertであり、今回のteardown変更による
退行としてgreenへ丸めていない。現行archive契約とt18受入は上記実teardown harnessで検証した。

## 監査で見てほしい点

1. run-bridge停止→landing読出し→runtime削除の順序になっていること。
2. 未pushのclosed runが`landed:false`と本数を出し、exit 0を維持すること。
3. CLI不在やlanding command失敗だけはloudにteardown失敗へ反映されること。
4. 親向け手順がcloseとlandingを混同せず、古いglobal CLIへ黙って寄らないこと。
