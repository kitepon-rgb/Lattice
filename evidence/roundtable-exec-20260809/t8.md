## 何を作ったか

設計メモの3点を run-bridge へ入れた。

### 1. idle 選定（seat-status-bridge の busy 判定を流用）

`seatBusyState(seat)` を足し、pane の末尾14行に **`esc to interrupt`** が在るかで `busy` / `idle` / `dead` を
判定する（`tmux capture-pane -p` の読み取りだけ・席へは1バイトも送らない）。**スピナーの語では判定しない**——
Claude 席は動名詞を毎回変えるので語で照合すると全席 idle に見える。`esc to interrupt` は Claude 席の
ステータス行にも Codex 席の `Working (…)` にも入る共通 marker なので vendor 分岐が要らない。

選定は **idle を先に当て、idle が尽きたら busy へ配る**。busy でも配車自体は禁じない——**席は辞退できるし、
全席 busy の時に配車を止めると卓が進まなくなる**。busy へ回した時はその旨をログへ出す。

### 2. `[辞退]` → 別席へ再配車

t4 で入れた分（辞退した席を候補から外して配り直す）をそのまま土台にし、占有判定を
`TERMINAL_ENTRY_STATES`（`done`/`unrecoverable`/`invalid`）基準へ揃えた。

### 3. `lattice run observe` polling → receipt 結果を room へ

**run は order から知る。** `worktree_path` は `<repo>/.lattice/runs/<run-id>/worktrees/…` なので、
そこから run dir を切り出す（`runDirOf`）。**別 config を増やさずに済み、複数 run が同時に走っても取り違えない。**

10秒ごとに `lattice run observe --run <dir>` を read-only で叩き、**要約が前回と変わった時だけ** room へ
1行返す（`[run] <run-id> accepted=[…] terminal=[…] hold=N conflict=N closed=…`）。**変化が無い間は鳴らさない**——
卓の全席を無駄に起こさないため。observe 自体が失敗した時は黙らず、理由を1行ログへ出す（他 run の報告は止めない）。

CLI は `--lattice <path>`（任意・既定は PATH の `lattice`）で差せる。**release 前の source tree を実測する時**に
要る——PATH の install は古い版で、新しい run store を `INVALID_RUN_STORE` と誤判定しうる（t7 で実測）。

## どう確認したか

`experiments/run-bridge-multiseat-repro.mjs`（新規）を実 tmux 3席 ＋ 偽 room server ＋ stub `lattice` で回した。
**8項目すべて green**:

```
OK ① busy な席を避けて idle な席へ配車する      — → msidle1（busy に見せた席は msbusy）
OK ② 辞退で別の席へ配り直す                     — msidle1 → msidle2
OK ②b 辞退した席へは戻さない
OK ②c busy な席は最後まで選ばれない             — → msidle2
OK ③ idle が尽きたら busy な席へ配車する（止めない） — → msbusy
OK ④ run 進行を room へ1行で返す                — [run] ms-run-1 accepted=[] … closed=false
OK ④b 変化が無い間は鳴らさない                  — 1 → 1 件
OK ④c 変化したら鳴らす                          — [run] ms-run-1 accepted=[T1] terminal=[T1] … closed=true
```
①→②→③は**同じ order を辞退で押し出していく形**なので、「idle を優先し、尽きたら busy、辞退した席へは
戻さない」が1本の流れとして確かめられている。④は stub の状態を書き換えて**変化の有無で鳴き分ける**ことを見た。

**実 Lattice は使っていない。** order/report の契約と一気通貫は t7 の
`run-bridge-e2e-repro.mjs` が実物（実 room・実席・実 controller）で見ており、こちらは席選定と room 投稿だけを
対象にしている。**この repro が green でも t7 の代わりにはならない。**

### 測定器の不備を1つ踏んだ（実装の欠陥ではない）

最初、busy に見せる席の pane に marker を**上端**へ印字したら「idle」と判定され、①が落ちた。
原因は `capture-pane -p` が pane の全行（末尾は空行）を返し、判定が**末尾14行**しか見ないこと。
**実席（Claude/Codex）は全画面 TUI でステータス行を最下部へ描く**ので末尾に入る——つまり
判定ロジックは正しく、私の作った偽席が非現実的だった。marker を下端へ置き直して①が green になった。
この経緯は repro のコメントへ残した。

## t8 に入れていないもの（scope の線引き）

- **席の状態を room の members へ送る**のは `seat-status-bridge` の仕事で、こちらは判定を読むだけ。二重化しない
- **複数 order の同時配車**は既に t4 の占有判定で成立している（1席1 order）。**同時に複数 run を回す受入は t11**
- **待機の可視性**（`run activate` が無言で待つ問題）は t7 の申し送りのまま。今回の `[run]` 投稿は
  run の進行を返すもので、**dispatch 応答待ちそのものは見えない**

## 見てほしい点（監査依頼）

1. **busy でも配車する判断。** 「idle が尽きたら busy へ配る」は卓を止めないための選択だが、
   busy な席へ配ると受諾が遅れる。**待たせるより配る**が正しいか、別の目で見てほしい
2. **`worktree_path` から run dir を切り出す方法**（`runDirOf`）。`.lattice/runs/<id>/worktrees/` という
   配置に依存している。配置が変わると静かに run を見失う（`null` を返して observe しなくなるだけで、
   配車自体は動き続ける）——loud に落とすべきかは判断が要る
3. **10秒 polling の粒度**と、`[run]` を全員宛にしていること。変化時だけとはいえ全席を起こすので、
   宛先を親だけにする案もある
