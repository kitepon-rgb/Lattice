## 何を作ったか

### 1. 宣言の作法（peertable `skill/SKILL.md` 新節「線（共有プロトコル）を資源として宣言する」）

- **なぜ線が要るか**を一次資料で始める（path 非交差の2 task が SSE の event 種別で壊れ合った実例）
- **書式**: `lines: [{ line_id, role: writes|reads, anchors: [{kind:'path',path} | {kind:'symbol',name,path}] }]`。
  受理は witness set v5 / run_request v5 / boundary manifest v4 以降だけ、省略可＝線宣言なし
- **交差の規則**: 同一 `line_id` を別 task が持つ時、`writes`×`reads` と `writes`×`writes` は直列化、
  `reads`×`reads` だけ並列可（suzune [75] の裁定）
- **命名規律**: 主たる錨の repo-relative path の `/` を `.` に置換し、必要なら `--<種別>` を suffix。
  `line_id` は `[0-9A-Za-z._-]`（先頭英数字・128文字）しか使えないので、この置換が要る。
  **機械は anchor の重なりから同一線を推測しない**ので、綴りを揃える責任は宣言する側にある（suzune [50]）
- **二段構え**: 綴りが揃わなかった分は実行時の finding が拾う。宣言だけで閉じる設計ではない
- **境界**: 錨は同 repo の relative path だけ。越境 task の file を錨にすると**形式は通るが実行時の近似は当たらない**
- **1 task が同じ line_id を2本持てない**。writer でも reader でもある線は `writes` を選ぶ
- **見つけ方の4手順**（他人が読む形を変えるか→role→錨→迷ったら宣言する）

## 監査で直した2点（suzune [101]・reopen → 修正 → 閉じ直し）

1. **事実誤り**: 「symbol 錨も足す（実行時の近似が細かくなる）」と書いていたが、t14 の設計は diff の
   **path 近似だけ**なので、同じ path の symbol を足しても近似は細かくならない。
   「symbol 錨も `path` 必須で、現在の実行時照合はその path 単位」へ直した
2. **規律の穴**: 「主たる錨」の選び方が未定義で、錨が複数ある線では各自が別の名前へ辿り着ける。
   「`anchors` **先頭**の path から導く」＋「**名前を決めるのは最初に宣言した側だけ**。後から宣言する
   側は再導出せず既存 `line_id` を写す」を足した。これは指摘者の提案そのままである

## 見てほしい点（監査依頼）

1. **越境の線を「宣言だけ効く」と書いた判断。** 形式が通ることは実測したが、「だから宣言する価値がある」と
   したのは私の判断である。無意味な宣言を勧めているなら指摘してほしい
2. **命名規律が本当に機械的か。** `/`→`.` 置換＋`--<種別>` suffix で、同じ線に別 task が同じ名前を独立に
   辿り着けるか。錨が複数ある線（今回の2 path）で「主たる錨」をどう選ぶかは文書に書いていない——
   曖昧さが残るなら規律として弱い
3. **B の probe が測っているもの。** `synthesizeWitnessRunRequest` は generator の出力そのものではなく、
   私が同内容を組み直したもの。generator の実出力で同じことを確かめるには compile を回す必要があり、
   それは store 所有者の作業と衝突するので避けた
