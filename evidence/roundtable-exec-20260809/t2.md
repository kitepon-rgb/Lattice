# t2 observe長寿命化（Lattice）

## 作成したもの

- `runtime-cli.mjs` の scripted controller 観測から固定120秒deadlineを除き、workerの実終了・typed failure・外部停止までsupervisorが観測を続けるようにした。
- `runtime-managed-supervisor.mjs` のcontrol journalを状態遷移の記録へ絞った。`running` observationは応答だけ返して耐久記録せず、`checkpoint_ready`・`held`・`terminal`は従来どおり記録する。
- controller heartbeatは毎回memory上のlivenessと単調sequenceを更新し、耐久記録は初回または`lease_set_digest`変化時だけ行う。これにより長寿命workerの壁時計に比例したjournal成長を止めた。

## 根因の実測

修正前の実daemonで125秒workerを動かすと、activateは約14.7秒後に`RUN_OUTCOME_UNKNOWN`を返し、123.2秒点でsupervisorが消えていた。run storeは`running=[T1]`、`run resume`も`dispatchable=[]`・`running=[T1]`のままで、workerを回収するobserverが残らなかった。

固定deadlineだけを外した後も70秒workerが約66秒で同様に消えた。activation ledgerを20ms間隔で捕捉し、次のtyped failureを確認した。

```text
ADAPTER_CONTROLLER_UNAVAILABLE
artifact契約違反: node数が上限を超えている
```

control storeは追記のたびにjournal全体をcanonical artifact化する一方、20msの`running` pollとheartbeatを全件追加していた。`MAX_EVENTS=100000`より先にartifactの`MAX_NODES=10000`へ到達し、supervisorがsignal記録なしで終了することが根因だった。

## 確認

- 実daemon・125秒workerの最終probe: 123.1秒点で`supervisor_exists=true`、`status.running=[T1]`、`resume.dispatchable=[]`、`resume.running=[T1]`。125.6秒後に`accepted=[T1]`、run event 8件、event chain valid。control journal末尾はdispatch 1件と初回heartbeat 1件で、`running` pollの時間比例増加なし。
- `node --test test/runtime-managed-supervisor.test.mjs`: 12/12 green。同一lease集合のheartbeatを初回だけ記録し、lease集合変化を再記録すること、`running`を記録せず3種の非running観測を記録することを固定した。
- HEAD＋t2の2pathだけを適用した隔離cloneで`node --test test/runtime-conflict-cli.test.mjs`: 10/10 green。共有treeでは同時実装中のt14差分により1件が一時的に`ADAPTER_CONTROLLER_UNAVAILABLE`となったが、同じcaseは隔離cloneでgreenとなり、t2単体の回帰でないことを対照確認した。
- `npm run check`: syntax check 145 files、green。

`run observe`・`run status`が読むrun storeと、今回間引いたsupervisor内部のcontrol journalは別系統である。利用者向けの`running`・`accepted`・`terminal`投影は削っていない。
