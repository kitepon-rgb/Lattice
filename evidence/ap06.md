着手前に既存3 testの被覆を読んだ。**どれも実CLIのstdoutを見ていなかった。**

| 既存test | 見ている面 |

| `todo-status-audit-pending.test.mjs`（ap03） | `projectTodoStatus(store)`。module境界の内側 |

ap03の実装と消費者（dotagents・ap08）の間に、誰も渡っていない継ぎ目が残っていた。
新規 `test/todo-audit-pending-e2e.test.mjs` はそこを埋める。全9 testが`bin/lattice.mjs`をspawnする。

ファイル名は design memo が指定した `test/todo-audit-pending.test.mjs` を使えなかった。ap02で

## 固定した事実

### (a) 表出と優先順位

- 全taskがdone → `audit_pending`にgate_ready entry 1件。`implicit: true`、
  slots `['terminal-audit']`、`next_commands`はreviewとclose-unauditedの2件。
- ready taskが他planに残る間は`next_action.reason`がready側（ADR 0063の優先順位を監査で上書きしない）。
- readyが尽きた時、`reason`は`no_ready_task`ではなく`audit_pending`。`state`は`ready`のまま。
- **返された次の一手を実際に実行した。** `<text>` placeholderだけ埋めて`spawnSync`へ渡し、exit 0と
  状態が`reviewing`へ進むことを確認。案内が実行可能であることを文字列比較で済ませない。

### (b) 遷移の全枝

gate_ready → review → **reject → reopen** → review → accept → 空、および close-unaudited → 空。

**rejectedの枝は既存testの誰も踏んでいなかった。** `rejected`は「判断が着いた」ではなく
「差し戻して待っている」なので監査待ちに残り、案内は`reopen`1件だけになる。共有moduleの分類で
一番間違えやすい点（ひなの [49] が ap02 で理由を書いて残したと言っている箇所）をE2Eで押さえた。

### (c) 混在——ADR 0062・ADR 0147裁定5のanchor

同じtask状態の store を2つ作った。片方は`audited`がgate_readyのまま、もう片方は監査だけacceptで
着けた。両者の`active_set`／`next_ready`／`blocked`／`dispatch_frontier`を`JSON.stringify`で
**byte比較**し、`frontier_digest`も個別に固定した。

2 storeを互いに比較するだけでは、両方同時に壊れた場合に通ってしまう（vacuous）。`next_ready`が
実際に`['P']`であることをリテラルでも固定して塞いだ。ひなのが [46] で別実装の突き合わせに対して
同じ対策を取っていて、独立に同じ罠へ気づいた形になっている。

### (d) 宣言Phase plan

- `implicit: false`でplan由来のslots（`['heavy']`）が出る。暗黙Phaseと区別できる。
- **後続Phaseは先行がacceptedになるまで`locked`で、gate_readyにはならない。** 全taskがdoneでも
  監査待ちに出るのは先頭Phaseだけ（すずめが [39] で報告した挙動をE2Eで固定した）。
- accept後にphase-2がlockedから解けて監査待ちへ入れ替わる。

### (e) 契約の自証

上位キーがexact 9件、`validateTodoStatusResult`がtrue、`result_digest`が`todoSelfDigest`と一致。
`audit_pending`を落としたv4形と、`phase_status: 'accepted'`を混ぜた形はどちらもvalidatorが拒否する。

### 既存のdispatch不変testへの併記（design memoの要求）

`test/todo-terminal-audit.test.mjs`の「終端監査gateはdispatchへ影響しない」testへ、
gate_ready時点で`audit_pending`が埋まること・reviewingで追従すること・accept後に空になることを
足した。**不変だけを固定すると、監査待ちが表出していない状態でもこのtestは緑のまま通る。**
表出と不変は片方ずつでは守れないので、同じ場所で両方を見る形にした。

## 実挙動で直した期待値（実装は変えていない）

1. ready 1件の時、`next_action.reason`は`parallel_frontier_present`ではなく`next_ready_present`
   （2件以上でparallel）。ready側が2つのreasonに分かれている。room [48]で共有し、すずめが
   ap07のADRへ反映した [50]。
2. **`close-unaudited`は後続Phaseを解かない。** acceptだけが解く。非対称を実測で確認し、
   独立したtestとして固定した（下記の観測を参照）。

## 観測——判断が要るなら別ToDo（この工程の受入条件外）

宣言Phase planの非終端Phaseを`close-unaudited`で閉じると、後続Phaseは`locked`のまま残り、
`audit_pending`は空になる。実測:

```
close前: [('phase-1','gate_ready'), ('phase-2','locked')]
close後: [('phase-1','closed_unaudited'), ('phase-2','locked')]  audit_pending: []
```

`accepted`は後続を解くので、これは「監査せず閉じるのは受入ではないから後続の前提を満たさない」
という設計として一貫している。工程を畳むなら全Phaseを畳む（`todo phase baseline`）のが正しい
使い方で、途中の1つだけを閉じる操作ではない。

ただし**「閉じたのに何も案内されない」状態が作れる**ことは事実で、この工程が直している
「機械が黙って残作業を隠す」と形が似ている。**欠陥だと主張はしない**——設計として説明が付くし、
再現には非終端Phaseへ`close-unaudited`を単独で使うという誤用が要る。testで挙動を固定して
コメントに理由を書いた。扱いを変えるならオーナー宛の議題で、ap06の受入条件外である。

## 検証

すべて `LATTICE_DASHBOARD_AUTOSTART=0` 付き（付け忘れると実dashboard daemonを起こして
`PROJECT_ROOT_CONFLICT`で落ちる。すずめが [24] で切り分けた既知の形）。

| 検証 | 結果 |
| --- | --- |
| `node --test test/todo-audit-pending-e2e.test.mjs` | 9 pass / 0 fail |
| 監査待ち関連8ファイルまとめて（ap02〜ap06の全test＋close-unaudited） | 48 pass / 0 fail |
| `npm run check` | syntax check passed: 140 files |

**`npm run ci`は回していない。** 3人が同時にtestを回して互いの負荷で遅くなっていたため、
ひなの [49] の提案（全員が手を止めてから1人が1回）に従い、私の`npm test`も途中で止めた。
止めた時点で結果は出ていないので、緑も赤も主張しない。受入ゲートのciはすずめが引き受ける
（bell [56]が合図を「ap06 done報告」と定めた）。

なお、3プロセス同時だった時と単独時で同じE2E testの所要が **6.7秒 → 0.5秒** まで変わった。
並行してfull testを回すのは無意味なだけでなく、時間予算を見るtestを偽陽性で落とす条件でもある。

## 次に書く人へ（新testの冒頭コメントにも焼いた）

実storeでgate_readyを作る時の落とし穴2つ。私はここで2往復払った。

1. `NOW`を現在時刻より先に置くと`STORE_INCONSISTENT / future_clock_skew`でstatusごと落ちる
   （許容5分）。既存testが過去日付の固定NOWを使っているのはこのため。
2. `buildTodoPlan`のtask入力は`{task_id, title, lane, narrative_ref, narrative_anchor,
   compile_binding, parent_task_id}`ちょうど。`design_memo`を足すとschema violationで弾かれる。

## fixtureを寄せなかった判断

repoにある実store fixtureは3箇所になった（ひなののgantt・すずめのap03・本test）。**寄せていない。**
私の (b)(c) は「2 plan混在＋Phase遷移を順に進める」形を要求し、既存2つの「1 planを
gate_readyにする」とは必要な形が違う。共通化するとhelperが全ケースの和集合を抱えて、どのtestが
何を要求しているか読めなくなる。代わりに落とし穴を冒頭コメントへ書いた。room [44]で宣言し、
ひなの [46]・すずめから異議なし。
