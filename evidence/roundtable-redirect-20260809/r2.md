# r2 pull型への組み替え: run-bridge・member.md（peertable・越境）

## 実施

Peertable 側から**装置が席へ仕事を配る向きを撤去**した。実体は Peertable repo にあり、
**詳細な証跡は `peertable:evidence/roundtable-redirect-20260809/r2.md`（本書より厚い）**が持つ。

- `skill/scripts/run-bridge.mjs`: 605行 → 255行。席選定・`[配車]`・`[受諾]`/`[辞退]` の再配車・
  work report 書込・work order 契約の複製・SSE を撤去し、`run list` と `run observe` の read-only
  中継だけにした。**書き込み経路は自分の pid 記録1つだけ**で、spool にも run store にも書かない。
  介入（hold）は `intake.actor.agent` 宛へ返す（r1 で公開してもらった欄）
- `skill/scripts/launch-seat.sh`: 席が自分の pid を知る経路として `.team/seats/<name>.json` を新設。
  6欄が `lattice.pull_worker_attach_input.v1` の exact 集合から `schema` を除いたものと一致するので、
  席は読んで `schema` を被せるだけで attach input になる。**raw argv は持たせない**（Codex 起動の
  argv に token が載るため digest だけ）。掃除は起動時に自分の分だけ（ADR 0157）
- `skill/templates/member.md` / `skill/SKILL.md` / `skill/templates/charter.md`: 向きごと書き換え。
  `claim`→`todo start`→`run intake`→`intervention` 判定→`attach`→作業→`todo done`→`accept`。
  **1席1 active intake** を明文化し、worktree の記述の誤り（畳むのは `abandon` だけ）を訂正した
- `skill/scripts/setup.sh`: work-order adapter binary の必須化・spool 作成・`run adapter register` を撤去。
  **adapter binary が無い環境でも卓が立つ**ようになった
- `skill/scripts/teardown.sh`: landing 読み出しを spool の order 逆算から `run list --json` へ組み替え
- Peertable commits: `e9bec7c` → `de7794b` → `ea9e594` → `ea1792b` → `e8f1e72`

## 確認

- 実測項目とその負の対照は peertable 側の証跡が全部持つ（seat record の秘密非複製を
  **token が argv に載っている Codex 席**で確認した負の対照、旧 CLI 引数が動作中の bridge を
  殺さないこと、teardown parser の正2＋負5 など）
- `bash -n` / `node --check` / `git diff --check`: green
- **`bash -n` は inline Python を検査しない。** teardown の parser は本文から
  **un-escape せずに exact bytes を抜いて**実 Python へ通した実測が証拠である

## 監査で直した4件（すべて他席の発見）

1. **charter/setup/teardown に旧 push が現行規範として残っていた**（mio）——bridge と member だけ
   pull 化しても、setup が立てる新しい卓へ旧契約が戻る
2. **seat record の `session` が `peer-<name>`** で、attach が `input.session === actor.session` を
   要求するため**必ず拒否される**（mio・suzune）
3. **teardown の `cmd | python3` が CLI 失敗を「active run なし」へ化かしていた**（suzune）
4. **その修正で書いた parser が Python 構文エラーで、全入力が同じ error で落ちていた**（kanade）。
   さらに**私が置いた repro は抽出時に `\"` を修復しており、測る前に測定対象を直していた**
   （mio・kanade・akari・suzune が独立に確認）。repro は削除した

## 宣言境界の膨張（3種類が同じ task に出た）

- `pt-launch-seat` — **上流由来**（r1 の attach 契約確定に追従）
- `pt-skill-md` — **自変更由来**（配車撤去で SKILL.md の起動 command が動かなくなった）
- `pt-charter-md` / `pt-setup-sh` / `pt-teardown-sh` — **見落とし由来**（元から向きが埋まっていた）

`scope-split-20260809` の s1 が `scope_expanded` を記録する時、この3種は別物として扱う価値がある。
抑えたいのは4つ目（思いつきで盛る）であって、前3つは追従・後始末・修復である。
